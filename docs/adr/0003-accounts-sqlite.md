# ADR 0003. Аккаунты, почта и синхронизация прогресса на SQLite

Статус: принято
Дата: 2026-10-13

## Контекст
Ученику нужен аккаунт: вход по email и паролю, подтверждение адреса, сброс пароля,
перенос прогресса между устройствами, лимит ИИ-разборов на человека, а не на устройство.
По соглашению общего сервера (`bronus-core/host/README.md`) проекты с базой данных используют общий PostgreSQL.
Ограничения Navyk:
- сервер без внешних зависимостей (`npm` недоступен, только встроенные модули Node.js 22);
- данных мало: несколько небольших таблиц, прогресс — один JSON-блоб на ученика (до 256 КБ);
- один контейнер, один процесс; запись редкая (вход, сохранение прогресса).

## Решение
1. **SQLite через встроенный `node:sqlite` (`DatabaseSync`)**, файл `$DATA_DIR/navyk.sqlite`
   в именованном томе Docker `navyk-data` (контейнер остаётся `read_only`). Журнал WAL,
   `busy_timeout`, внешние ключи. Миграции — список в `server/src/db.ts` и таблица `migrations`;
   применяются при старте, только вперёд.
   Драйвер PostgreSQL потребовал бы зависимость из npm или собственную реализацию протокола — оба варианта хуже.
2. **Таблицы:** `users`, `sessions`, `tokens`, `progress`, `email_log`.
   Секреты в открытом виде не хранятся: пароль — scrypt (N=2^15, r=8, p=1, соль 16 байт, ключ 64 байта,
   формат `scrypt$N$r$p$salt$hash`), сессии и одноразовые токены — SHA-256, адрес в `email_log` — SHA-256.
   В логах нет адресов, паролей, токенов и ссылок из писем (кроме провайдера `log` в разработке).
3. **Резервные копии:** `VACUUM INTO` — целостная копия без остановки приложения и без утилиты `sqlite3`.
   Таймер `navyk-backup` (03:30 UTC) → `/data/backups` и `/var/backups/navyk` на сервере, 14 дней.
4. **Почта** — HTTP API провайдера через `fetch` (Brevo или Resend, `EMAIL_PROVIDER`), без SMTP-библиотек.
   Письма отправляются в фоне: ответ API не ждёт провайдера, сбой отправки не меняет ответ (202) и
   записывается в `email_log`.
5. **Прогресс:** сервер хранит блоб целиком, слияние делает клиент (`web/js/engine/sync.js`);
   `updatedAt` строго растёт.

## API (контракт с клиентом)
Все изменяющие запросы к `/api/*` (POST, PUT, PATCH, DELETE) требуют заголовок `Origin`, равный `PUBLIC_ORIGIN`,
иначе `403 {error:"forbidden_origin"}`. Сессия — cookie `__Host-navyk_session` (`Secure; HttpOnly; SameSite=Lax; Path=/`),
32 случайных байта, скользящий срок 30 дней; в разработке (`COOKIE_SECURE=false`) — `navyk_session` без `Secure`.

| Запрос | Ответ |
|---|---|
| `POST /api/auth/register {email,password,lang}` | `202 {ok:true}` всегда; `400 invalid_email / weak_password` |
| `POST /api/auth/confirm {token}` | `200 {user}` + cookie; `400 invalid_token` (24 ч, одноразовый) |
| `POST /api/auth/resend-confirmation {email}` | `202 {ok:true}` всегда |
| `POST /api/auth/login {email,password}` | `200 {user}` + cookie; `401 invalid_credentials`; `403 email_not_confirmed` (только при верном пароле); `429 {error:"locked",retryAfter}` после 5 ошибок, 15 мин |
| `POST /api/auth/forgot {email,lang}` | `202` всегда; ссылка сброса живёт 1 ч |
| `POST /api/auth/reset {token,password}` | `200 {user}` + cookie (подтверждает адрес, завершает все прочие сессии); `400 invalid_token / weak_password` |
| `POST /api/auth/logout` | `204`, cookie очищается |
| `GET /api/auth/me` / `PATCH /api/auth/me {lang}` | `200 {user:{id,email,lang,createdAt}}`; `401` |
| `GET /api/progress` | `200 {data,updatedAt}` (`null,null` если ещё нет); `401` |
| `PUT /api/progress {data,baseUpdatedAt}` | `200 {data,updatedAt}`; `413` больше 256 КБ; `401` |

Защита от злоупотреблений: 20 запросов к `/api/auth/*` в минуту с IP и 3 письма в час на адрес → `429 {error:"rate_limited",retryAfter}`.
Пароль: 8–128 символов, не из списка частых, не совпадает с адресом.

**Без перечисления аккаунтов.** `register`, `resend-confirmation` и `forgot` отвечают одинаково для любого адреса.
Если адрес уже подтверждён, `register` отправляет письмо «у тебя уже есть аккаунт» со ссылкой сброса.
Для неизвестного адреса вход проверяет хеш-пустышку (одинаковое время) и ведёт такую же блокировку после 5 ошибок.
Повторная регистрация неподтверждённого адреса не меняет пароль сразу: новая ссылка подтверждения несёт хеш пароля
своей регистрации и включает его только при переходе по ней. Так посторонний не может ни захватить адрес,
ни подменить пароль владельца.

## Почему не PostgreSQL сейчас
- ноль зависимостей и ноль дополнительных сервисов: нечего обновлять и настраивать вручную (требование автономности);
- объём (тысячи–десятки тысяч учеников, килобайты на каждого) далеко в пределах SQLite;
- одна запись в секунду на ученика в худшем случае — WAL справляется с запасом.

## Когда переходить на PostgreSQL
Любое из условий:
- больше одного экземпляра приложения (горизонтальное масштабирование, отдельный воркер);
- устойчиво больше ~200 записей в секунду или ошибки `SQLITE_BUSY` в логах;
- база больше нескольких ГБ, нужна аналитика или point-in-time-восстановление;
- сертификаты, платежи и другие данные, к которым обращаются несколько сервисов.
Переход: та же схема в PostgreSQL общего сервера, однократный перенос данных скриптом,
адаптер в `server/src/db.ts`. Лимиты из памяти процесса (`limits.ts`) тогда же переезжают в Redis или PostgreSQL.

## Последствия
- Новое на сервере: том `navyk_navyk-data`, таймер `navyk-backup`, переменные `PUBLIC_ORIGIN`, `EMAIL_*`
  (`docs/infra/hetzner.md`, `deploy/set-email.sh`).
- Копии лежат на том же сервере; внешнее хранение (Hetzner Backups / Storage Box) — решение владельца, платное.
- GDPR: храним только адрес, хеш пароля, язык и прогресс. Удаление аккаунта и выгрузка данных — следующий шаг
  (`DELETE FROM users` каскадно удаляет сессии, токены и прогресс).
- `node:sqlite` в Node 22 помечен экспериментальным: сервер запускается с `--disable-warning=ExperimentalWarning`;
  при обновлении Node проверять `npm test`.
