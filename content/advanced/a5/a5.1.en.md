::: step hook
Emma manages projects for clients. Every Friday she sends them a report, and every time she pastes the same wall of text into the chat:

```prompt
Write a report for the client. Remember: start with the week's headline, then "Done", "In progress", "What we need from you". Polite, no jargon, under 200 words…
```

Twenty Fridays in a row, the same thing. Could she explain it once and never repeat it again?
:::

::: step explain
She could. That's what a *skill* is for: a folder of instructions, sometimes with templates and scripts too.

Picture an experienced colleague with a shelf of folders: “How we write reports”, “How we format presentations”. They don't keep them all open all day. When a report comes up, they pull out the right folder and follow it.
:::

::: exercise single_choice
id: "a5.1.e1"
type: "single_choice"
question: "Which description of a skill is the most accurate?"
options:
  - text: "A folder of instructions and materials for a particular kind of task, which Claude opens when the task fits"
    correct: true
    why: "Exactly. A skill is a ready-made procedure: how to do the report, how to format the presentation. Claude pulls it out when needed rather than keeping it open all the time."
  - text: "A separate, smarter version of Claude that you have to buy"
    correct: false
    why: "A skill doesn't change the model or make Claude “smarter”. It gives Claude your rules and materials for a specific task, like a briefing sheet for a new hire."
  - text: "A record of all your past chats that Claude rereads before answering"
    correct: false
    why: "That's closer to memory, which the “Memory and settings” module covered. You write a skill yourself as a set of instructions; it isn't assembled from your chat history."
  - text: "A rule that applies in every chat, all the time, whatever you ask"
    correct: false
    why: "That's how Instructions for Claude in your settings work. A skill only kicks in when the task fits: a client report, not a lasagne recipe."
hint: "Think of the colleague with the shelf of folders. Do they keep every folder open all day, or pull out the one the task needs?"
:::

::: step explain
How does Claude know which folder to pull out? Every skill has a name and a short description. That's all Claude sees, like the spines of folders on a shelf.

If the request fits, Claude opens the instructions. It reads extra files only when they're needed. This is called *progressive disclosure*: a dozen skills use almost no context until one of them is needed.
:::

::: exercise order_steps
id: "a5.1.e2"
type: "order_steps"
question: "Emma writes: “Put together the Friday report for the client.” Put what happens next in order."
shuffle: true
items:
  - text: "Claude looks at the names and descriptions of all enabled skills"
    why: "This is the first, lightest level: Claude sees only the “spines”, not what's inside the folders."
  - text: "It finds a skill whose description matches “report for the client”"
    why: "The decision is made from the description. That's why a good description is the most important part of a skill; there's a separate lesson on it."
  - text: "It loads that skill's instructions"
    why: "Only now does the full text enter the context: the report's structure, tone and length."
  - text: "If needed, it opens extra files from the folder, such as a template"
    why: "Templates and reference files are read last, and only if needed. All the other skills and files stay closed."
  - text: "It writes the report following Emma's rules"
    why: "Emma no longer pastes in the wall of rules: Claude took everything it needed from the skill on its own."
hint: "Go from light to heavy: spines first, then the folder, then the attachments, and only at the very end the actual work."
:::

::: step explain
Don't confuse a skill with things you already know:

- a *project* is background knowledge that's always loaded in that project's chats;
- *Instructions for Claude* are general rules for every conversation;
- a *connector* is access to a service, such as your email or cloud drive.

A skill is a procedure for a task. It switches on when needed and isn't limited to a single project.
:::

::: exercise match_pairs
id: "a5.1.e3"
type: "match_pairs"
question: "Match each tool with what it gives Claude."
pairs:
  - left: "Project"
    right: "Files and context for one topic, always at hand in its chats"
    why: "A project is the working folder for a topic: renovation materials, exam prep. They're loaded in every chat in the project, even when they aren't needed right now."
  - left: "Instructions for Claude"
    right: "General preferences that apply in every conversation"
    why: "For example, “use British English, keep it simple”. It's about you in general, not about a particular kind of task."
  - left: "Skill"
    right: "A procedure for a particular kind of task, which Claude pulls out when the task fits"
    why: "A client report, a presentation in your brand style, meeting minutes. Until a task like that comes up, the skill takes up almost no space."
  - left: "Connector"
    right: "Access to an external service: email, calendar, file storage"
    why: "A connector gives access to data, and a skill can teach how to use that data. They work well together."
hint: "Ask about each tool: is it “always on”, “on within one topic”, “switched on for a task”, or “opening access to a service”?"
:::

::: step explain
Which tasks are worth turning into a skill? The ones that repeat and follow the same rules every time. A skill replaces that wall of text you keep pasting into the chat.

A skill won't speed up a one-off task: just write a good prompt.
:::

  - text: "Making team presentations in the company's brand colours and fonts"
    correct: true
    why: "This is a classic example from Claude's help centre: one brand style, lots of presentations."
  - text: "Turning meeting notes into minutes: decisions, tasks, owners, deadlines"
    correct: true
    why: "Lots of meetings, one structure for the minutes. A skill saves you explaining the format every time."
  - text: "Coming up with a toast for a friend's wedding, once"
    correct: false
    why: "That's a one-off task. A good prompt with facts about your friend will work better than a skill you'll never use again."
  - text: "Finding out today's euro to dollar exchange rate"
    correct: false
    why: "This needs fresh data, not working rules. It's a job for search; a skill doesn't know today's rate."
hint: "Look for tasks that repeat and are done the same way each time."
:::

::: exercise write_prompt
id: "a5.1.e5"
type: "write_prompt"
question: "Describe a recurring task of yours as a future skill: what the task is, when it comes up, what rules to follow and what a good result looks like. Don't include real client names, phone numbers or passwords."
placeholder: "Every week I… It needs to be done like this: …"
ideas:
  - "How often the task comes up and how you usually ask for it"
  - "Who the result is for"
  - "Structure or template of the result"
  - "Tone and length"
  - "A typical mistake to avoid"
min_chars: 80
hint: "Imagine you're handing this task over to a new colleague for good: when to take it on, what to do, what the result should look like and why it's done that way."
review:
  task: "The learner describes a recurring task so that a Claude skill (a folder of instructions that Claude opens when a task fits) could be built from the description. A good description: it's clear what the task is and what the output is (R1); there's context — who the result is for, when the task comes up, why the rules are the way they are (R2); the shape of the result is set — structure, tone, length (R3); it's clear what a good result is and what to avoid (R4). Bonus: the learner names the words they usually use to ask for this task — useful later for the skill description. Don't require the SKILL.md format: the learner will study it later. If the task is a one-off, gently point out that a skill pays off on recurring tasks."
  criteria: ["R1", "R2", "R3", "R4"]
  reference_prompt: |
    Every Friday I write clients a progress report on their project (we build websites). I usually ask Claude like this: "client report", "weekly summary for the client".
    Clients aren't technical and read the report on their phone, so it needs to be short and jargon-free.
    Structure: one sentence on the week's headline, then three sections — "Done", "In progress", "What we need from you" (with a specific deadline).
    Tone: polite, calm and confident. If something is delayed, we say so plainly and propose a new date straight away.
    Length: under 200 words. A good report is one the client understands in a minute and knows what to do next.
  show_reference: true
  fallback_feedback:
    - "Is it clear what the task is and what the output will be?"
    - "Does it say when the task comes up and how you usually ask for it?"
    - "Does it say who the result is for and why the rules are the way they are?"
    - "Is the shape of the result described: structure, tone, length?"
    - "Is it clear what counts as a good result and what to avoid?"
    - "Does the task really repeat? A skill pays off on things you do again and again."
:::

::: step summary
**A skill is a folder of instructions for a recurring task. Claude sees only its name and description, and opens it when the task fits.**

A project holds a topic's knowledge, Instructions for Claude are rules for every chat, a connector is access to a service.
