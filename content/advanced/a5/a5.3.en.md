::: step hook
Emma has had enough of copying the Friday report rules into every chat. She's going to make her own skill.

Emma isn't a programmer. Will she need code? No: the simplest skill is a single text file.
:::

::: step explain
The minimal skill is a folder with a *SKILL.md* file. At the top there's a short header with two fields; below it, plain text:

```markdown
---
name: weekly-client-report
description: Prepares the Friday client report on project progress. Use when asked for a client report, a weekly summary or a status update for the client.
---
# Client report
1. First sentence: the week's headline.
2. Three sections: "Done", "In progress", "What we need from you".
3. Polite, no jargon: clients aren't technical.
4. Under 200 words.
```
:::

::: step explain
*name* is the skill's name, up to {{data.limits.a5_skill_name_max}}. It's safest to use lowercase letters and hyphens.

*description* is up to {{data.limits.a5_skill_description_max}}, and it's the most important part. Remember the spines on the shelf? That's all Claude sees, and it uses the description to decide whether to pull out the folder.

A good description says two things: what the skill does and when to use it.
:::

::: exercise single_choice
id: "a5.3.e1"
type: "single_choice"
question: "Sean is making a skill for meeting minutes. Which description will best help Claude know when to pull it out?"
options:
  - text: "“Turns meeting notes into minutes — decisions, tasks, owners, deadlines. Use when asked for minutes, a meeting summary or a call recap.”"
    correct: true
    why: "It has both what the skill does and when to use it. It lists the words Sean usually uses to ask for this task: “minutes”, “meeting summary”, “call recap”. Claude will easily recognise a matching prompt."
  - text: "“Helps with documents.”"
    correct: false
    why: "Far too vague: half of all prompts involve “documents”. Claude will pull out the skill when it doesn't belong or, the other way round, miss the moment it's needed."
  - text: "“My most useful skill, really good, use it often!”"
    correct: false
    why: "Not a word about what the skill does. Enthusiasm doesn't help Claude choose, and the description is the only thing it sees before opening the folder."
  - text: "“Minutes.”"
    correct: false
    why: "There's a topic, but no action and no signals for when to use it. Meeting minutes? Minutes of time? Claude would have to guess."
hint: "The description should answer two questions: what the skill does and in which situation to pull it out."
:::

::: exercise find_error
id: "a5.3.e2"
type: "find_error"
question: "Emma wrote a skill description. Tap the parts that stop Claude from choosing the skill correctly."
prompt: "A skill for reports. Prepares the weekly client report — done, in progress, what we need from the client. Use always, for any text. Use when asked for a weekly summary or a status update for the client."
segments:
  - text: "A skill for reports. "
    weak: true
    why: "An empty phrase: what reports? Financial ones, travel expense reports? It takes up space in a short description and clarifies nothing."
  - text: "Prepares the weekly client report — done, in progress, what we need from the client. "
    weak: false
    why: "Good: it's clear what the skill does and what the result will be."
  - text: "Use always, for any text. "
    weak: true
    why: "The main mistake. With this description Claude will drag the report format into birthday messages and recipes. A skill should only switch on for its own task."
  - text: "Use when asked for a weekly summary or a status update for the client."
    weak: false
    why: "Great: specific signals for when to pull out the skill, in the same words Emma herself uses in her prompts."
hint: "Look for phrases that clarify nothing, and phrases that would make the skill kick in where it isn't needed."
:::

::: step explain
Below the header, write how to do the job. Three tips from Claude's help centre:

- *start simple*: plain instructions, no scripts;
- *add an example* of a good result: it conveys style better than descriptions;
- *one skill, one task*: several small skills work better than one huge one.

Never put passwords or access keys in a skill.
:::

::: exercise build_prompt
id: "a5.3.e3"
type: "build_prompt"
question: "Assemble the body of Emma's skill, below the header. Leave out the blocks that don't belong."
blocks:
  - id: "b1"
    text: "You write the client report on behalf of the project manager: calm and confident."
    role: "role"
    why: "The role sets the report's voice: not a salesperson or a developer, but a manager who has things under control."
  - id: "b2"
    text: "Put the report together from the week's notes: the first sentence is the headline, then the sections “Done”, “In progress”, “What we need from you” with a specific deadline."
    role: "goal"
    why: "The main action and the structure. Without this block the skill doesn't do anything."
  - id: "b3"
    text: "Clients aren't technical and read on their phones, so write without jargon, politely, in under 200 words."
    role: "context"
    why: "Context with a reason. Knowing that clients read on their phones, Claude will avoid long paragraphs and technical terms on its own."
  - id: "b4"
    text: "Example of a good opening: “This week we launched the order form, and requests are already coming in.”"
    role: "format"
    why: "An example shows the tone and level of detail better than any description. The help centre recommends adding examples to a skill."
  - id: "b5"
    text: "Client's admin panel password: Dublin2026!"
    role: "noise"
    why: "Passwords and keys never go in a skill: a skill is a file that can be downloaded, forwarded or shown to someone. Connectors exist for accessing services."
  - id: "b6"
    text: "Be the best assistant in the world!!!"
    role: "noise"
    why: "Sounds upbeat, but doesn't say what to do. Claude is already trying; it needs concrete rules."
target_order: ["b1", "b2", "b3", "b4"]
hint: "Who is writing, what to do, for whom and why, what a good result looks like. Secrets and empty slogans stay out."
:::

::: step explain
How to install a skill:

1. Put SKILL.md in a folder. Folder name = name.
2. Compress the folder into a ZIP so that the folder itself sits at the root of the archive.
3. Open {{data.ui_paths.a5_customize_skills}} and click {{data.ui_paths.a5_upload_skill}}.

Only you can see your own skill. You can edit the text right there: select a passage and click {{data.ui_paths.a5_edit_with_claude}}.
:::

::: step explain
Now make your own skill. Take the task you described in the first lesson of this module, or any recurring one: meeting minutes, a reply to a standard complaint, a social media post.

Write a complete SKILL.md. Navyk will send it to Claude for feedback.
:::

::: exercise write_prompt
id: "a5.3.e5"
type: "write_prompt"
question: "Write a SKILL.md for your recurring task: a header with name and description (what it does and when to use it), then instructions and a short example. Don't include passwords, keys or real client data."
placeholder: "---\nname: …\ndescription: … Use when …\n---\n# …"
ideas:
  - "name in lowercase with hyphens"
  - "description: what it does + when to use it"
  - "The words you usually use to ask for this task"
  - "Steps or structure of the result"
  - "Who the result is for and why"
  - "An example of a good result"
min_chars: 120
hint: "Start with the header: name and description. In the description, answer two questions: what the skill does and when to pull it out. Below that, describe step by step how to do the job, for whom and why, and add a short example."
review:
  task: "The learner writes a SKILL.md file for their own Claude skill. This isn't a one-off prompt but a standing instruction that Claude will open when a request matches the description. Expected: YAML frontmatter with name and description, and instruction text below. Key point: the description says what the skill does and when to use it, with specific trigger words, up to 200 characters (assess under R1 and R4: if the description is vague, like “helps with texts” or “use always”, that's the main area for improvement). Instructions: a clear task and result (R1), context — for whom and why (R2), format — structure, tone, length (R3), a criterion for a good result and an example (R4, R6). Steps are a plus. Don't require scripts or code. If the skill contains passwords, access keys or real personal data, R10 applies: gently warn that a skill is a file that can be downloaded or forwarded, and don't repeat that data."
  criteria: ["R1", "R2", "R3", "R4", "R6"]
  reference_prompt: |
    ---
    name: meeting-protocol
    description: Turns meeting notes into minutes — decisions, tasks, owners, deadlines. Use when asked for minutes, a meeting summary or a call recap.
    ---
    # Meeting minutes

    The minutes are read by colleagues who weren't at the meeting, so they must make sense without context.

    1. First line: topic, date, attendees.
    2. "Decisions": a numbered list, one decision per item.
    3. "Tasks": a table of task, owner, deadline.
    4. "Open questions": anything left undecided. If there are none, write "none".
    5. Don't fill in gaps: if the notes don't name an owner or a deadline, write "not assigned".

    Length: one page at most, no introductions or conclusions.

    ## Example task row
    | Prepare a quote for the office refit | Andrew | 24 October |
  show_reference: true
  fallback_feedback:
    - "Is there a header with name and description between the --- lines?"
    - "Does the description say what the skill does and when to use it?"
    - "Does the description include the words you usually use to ask for this task?"
    - "Is the description too broad: could the skill kick in where it isn't needed?"
    - "Do the instructions say what to do, for whom and why?"
    - "Is the shape of the result set: structure, tone, length?"
    - "Is there an example of a good result?"
    - "Is the skill free of passwords, keys and real client data?"
:::

::: step summary
**A no-code skill is a folder with a SKILL.md file: a header with name and description, then instructions and an example.**

The description is everything: what the skill does and when to use it. If it doesn't kick in, edit the description and test again.
