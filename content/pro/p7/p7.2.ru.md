::: step hook
Андрей поправил в промпте одну фразу про тон. Проверил на трёх вопросах — бот стал теплее. Выкатил.

Через неделю пришли жалобы: бот начал называть тариф «Домашний 100» за 150 грн вместо 250. Эту ошибку никто не ловил, потому что никто не проверял цены после правки.

Как узнать о такой поломке до клиентов?
:::

::: step explain
Нужен *eval* — набор тестов для промпта, который прогоняют после каждой правки.

Несколько слов из статьи инженеров Anthropic:

- *задача* (task) — один тест: входные данные и критерии успеха;
- *оценщик* (grader) — логика, которая ставит балл;
- *транскрипт* — полная запись попытки.

Начинать советуют с 20–50 простых задач из реальных сбоев.
:::

::: step example
Самый простой eval — файл с задачами и проверка кодом:

```json
[
  { "id": "tariff-1", "input": "Сколько стоит «Домашний 100»?", "expect": { "contains": "250 грн" } },
  { "id": "empty-1", "input": "", "expect": { "handoff": true } }
]
```

```python
def grade(output: str, case: dict) -> bool:
    return case["expect"]["contains"].lower() in output.lower()
```

В Navyk так проверяют самого проверяющего твоих промптов: эталонный набор прогоняется при каждой правке его инструкции.
:::

::: step explain
Оценщики бывают трёх видов:

- *код*: точное совпадение, поиск строки. Быстро, дёшево и воспроизводимо, но без нюансов;
- *модель*: оценивает по рубрике, улавливает тон и смысл. Её надо сверять с людьми;
- *человек*: эталон, но медленно и дорого.

Документация советует автоматизировать, где можно: много тестов с автооценкой лучше, чем мало с ручной.
:::

::: exercise match_pairs
id: "p7.2.e1"
type: "match_pairs"
question: "Соедини критерий бота Андрея с самым подходящим оценщиком."
pairs:
  - left: "Бот относит обращение к одной из 4 тем: оплата, скорость, подключение, другое"
    right: "Код: точное совпадение с эталонной темой"
    why: "Ответ — одно слово из списка. Сравнение строк надёжно, мгновенно и бесплатно."
  - left: "Тон ответа сочувственный и спокойный, оценка по шкале 1–5"
    right: "Модель-оценщик с подробной рубрикой"
    why: "Тон кодом не поймать. Модель с рубрикой справится, а шкала 1–5 даёт число, которое можно сравнивать между версиями."
  - left: "Двадцать спорных диалогов, где даже команда не уверена, как правильно"
    right: "Человек"
    why: "Где нужна экспертиза и нет согласия, нужен человек. Его оценки заодно калибруют модель-оценщика."
hint: "Начинай с самого дешёвого способа, который справится. Код — для однозначных ответов, модель — для смысла и тона, человек — для спорного."
:::

::: exercise multi_choice
id: "p7.2.e2"
type: "multi_choice"
question: "Андрей собирает 30 задач для eval. Какие случаи обязательно стоит включить? Отметь все."
options:
  - text: "Реальные вопросы о тарифах, на которых бот уже ошибался"
    correct: true
    why: "Лучший старт — реальные сбои. Статья Anthropic советует начинать именно с задач из прошлых ошибок."
  - text: "Пустое сообщение и сообщение не по теме: «посоветуй сериал»"
    correct: true
    why: "Крайние случаи: отсутствующий или нерелевантный ввод. Документация прямо просит о них не забывать."
  - text: "Грубое сообщение с попыткой заставить бота выдать системный промпт"
    correct: true
    why: "Плохой или вредный ввод — тоже крайний случай. Бот должен вежливо удержаться в рамках."
  - text: "Вопросы, где бот должен передать клиента оператору, и вопросы, где не должен"
    correct: true
    why: "Сбалансированный набор: если тестировать только случаи «передай», бот научится передавать всех подряд. Однобокий eval даёт однобокую оптимизацию."
  - text: "Только самые типичные вопросы, на которые бот и так отвечает правильно"
    correct: false
    why: "Такие тесты всегда зелёные и ничего не ловят. Типичные случаи нужны, но в паре с крайними и проблемными."
hint: "Хороший набор похож на реальную жизнь: типичное, сломанное раньше, странное, грубое и случаи «да» и «нет» для одного правила."
:::

    why: "Без baseline (исходного результата) не поймёшь, улучшила правка что-то или нет."
  - text: "Изменить промпт и прогнать тот же набор"
    why: "Набор должен быть тем же, иначе сравниваешь не версии промпта, а разные тесты."
  - text: "Прочитать транскрипты проваленных задач"
    why: "Число показывает, что сломалось, а транскрипт — почему. Иногда ошибается не бот, а сам оценщик."
hint: "Сначала «что хорошо», потом тесты, потом исходный замер, затем правка и разбор провалов."
:::

::: step explain
Модель-оценщик — тоже промпт. По документации, хорошему оценщику нужны:

- подробная чёткая рубрика;
- конкретный вывод: «correct» или «incorrect», либо шкала 1–5;
- рассуждение перед оценкой.

И оценивать лучше другой моделью, чем той, что отвечала. Напиши такой промпт сам.
:::

::: step summary
**Каждая правка промпта — через один и тот же набор тестов.**

Начни с 20–50 задач из реальных сбоев и крайних случаев. Код — для однозначного, модель с рубрикой — для смысла и тона, человек — для спорного. И читай транскрипты провалов.
:::
