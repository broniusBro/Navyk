::: step hook
Paweł poprawił w prompcie jedno zdanie o tonie. Sprawdził na trzech pytaniach — bot zrobił się cieplejszy. Wdrożył.

Po tygodniu przyszły skargi: bot zaczął podawać cenę taryfy „Domowy 100” jako 39 zł zamiast 59 zł. Nikt nie wyłapał tego błędu, bo nikt nie sprawdzał cen po poprawce.

Jak dowiedzieć się o takiej usterce wcześniej niż klienci?
:::

::: step explain
Potrzebny jest *eval*, czyli zestaw testów dla promptu, który uruchamia się po każdej poprawce.

Kilka pojęć z artykułu inżynierów Anthropic:

- *zadanie* (task) — jeden test: dane wejściowe i kryteria sukcesu;
- *oceniający* (grader) — logika, która wystawia ocenę;
- *transkrypt* — pełny zapis próby.

Radzą zaczynać od 20–50 prostych zadań z prawdziwych awarii.
:::

::: step example
Najprostszy eval to plik z zadaniami i sprawdzenie kodem:

```json
[
  { "id": "tariff-1", "input": "Ile kosztuje „Domowy 100”?", "expect": { "contains": "59 zł" } },
  { "id": "empty-1", "input": "", "expect": { "handoff": true } }
]
```

```python
def grade(output: str, case: dict) -> bool:
    return case["expect"]["contains"].lower() in output.lower()
```

W Navyk tak samo sprawdza się model oceniający twoje prompty: wzorcowy zestaw uruchamia się przy każdej zmianie jego instrukcji.
:::

::: step explain
Oceniający bywają trzech rodzajów:

- *kod*: dokładne dopasowanie, wyszukanie ciągu znaków. Szybko, tanio i powtarzalnie, ale bez niuansów;
- *model*: ocenia według rubryki, wyłapuje ton i sens. Trzeba go porównywać z ocenami ludzi;
- *człowiek*: wzorzec, ale wolno i drogo.

Dokumentacja radzi automatyzować, gdzie się da: dużo testów z automatyczną oceną jest lepsze niż mało z ręczną.
:::

::: exercise match_pairs
id: "p7.2.e1"
type: "match_pairs"
question: "Połącz kryterium bota Pawła z najlepiej pasującym oceniającym."
pairs:
  - left: "Bot przypisuje zgłoszenie do jednego z 4 tematów: płatności, prędkość, podłączenie, inne"
    right: "Kod: dokładne dopasowanie do wzorcowego tematu"
    why: "Odpowiedź to jedno słowo z listy. Porównanie ciągów znaków jest niezawodne, natychmiastowe i darmowe."
  - left: "Ton odpowiedzi jest spokojny i empatyczny, ocena w skali 1–5"
    right: "Model oceniający ze szczegółową rubryką"
    why: "Tonu kodem nie wyłapiesz. Model z rubryką sobie poradzi, a skala 1–5 daje liczbę, którą można porównywać między wersjami."
  - left: "Dwadzieścia spornych rozmów, przy których nawet zespół nie jest pewien, co jest dobrze"
    right: "Człowiek"
    why: "Tam, gdzie potrzebna jest wiedza ekspercka i nie ma zgody, potrzebny jest człowiek. Jego oceny przy okazji kalibrują model oceniający."
hint: "Zaczynaj od najtańszego sposobu, który da radę. Kod do jednoznacznych odpowiedzi, model do sensu i tonu, człowiek do spornych spraw."
:::

::: exercise multi_choice
id: "p7.2.e2"
type: "multi_choice"
question: "Paweł zbiera 30 zadań do evala. Które przypadki koniecznie warto uwzględnić? Zaznacz wszystkie."
options:
  - text: "Prawdziwe pytania o taryfy, na których bot już się mylił"
    correct: true
    why: "Najlepszy start to prawdziwe awarie. Artykuł Anthropic radzi zaczynać właśnie od zadań z wcześniejszych błędów."
  - text: "Pustą wiadomość i wiadomość nie na temat: „poleć mi serial”"
    correct: true
    why: "Przypadki brzegowe: brakujące lub nieistotne wejście. Dokumentacja wprost prosi, żeby o nich nie zapominać."
  - text: "Niegrzeczną wiadomość z próbą zmuszenia bota do ujawnienia promptu systemowego"
    correct: true
    why: "Złe lub szkodliwe wejście to też przypadek brzegowy. Bot powinien uprzejmie pozostać w swoich ramach."
  - text: "Pytania, przy których bot powinien przekazać klienta konsultantowi, i takie, przy których nie powinien"
    correct: true
    why: "Zbalansowany zestaw: jeśli testujesz tylko przypadki „przekaż”, bot nauczy się przekazywać wszystkich jak leci. Jednostronny eval daje jednostronną optymalizację."
  - text: "Tylko najbardziej typowe pytania, na które bot i tak odpowiada poprawnie"
    correct: false
    why: "Takie testy zawsze są zielone i niczego nie wyłapują. Typowe przypadki są potrzebne, ale w parze z brzegowymi i problematycznymi."
hint: "Dobry zestaw przypomina prawdziwe życie: typowe sprawy, rzeczy, które się już psuły, dziwne, niegrzeczne oraz przypadki „tak” i „nie” dla jednej zasady."
:::

::: exercise order_steps
id: "p7.2.e3"
type: "order_steps"
question: "Ułóż kroki pracy z evals we właściwej kolejności."
shuffle: true
items:
  - text: "Zapisać kryteria sukcesu"
    why: "Bez kryteriów oceniający nie ma z czym porównać odpowiedzi."
  - text: "Zebrać 20–50 zadań z prawdziwych awarii i przypadków brzegowych"
    why: "Zadanie to wejście i oczekiwany wynik. Prawdziwe awarie dają najbardziej przydatne testy."
  - text: "Uruchomić obecną wersję promptu i zapisać wynik jako punkt odniesienia"
    why: "Bez baseline (wyniku wyjściowego) nie wiesz, czy poprawka cokolwiek poprawiła."
  - text: "Zmienić prompt i uruchomić ten sam zestaw"
    why: "Zestaw musi być ten sam, inaczej porównujesz różne testy, a nie wersje promptu."
  - text: "Przeczytać transkrypty zadań, które nie przeszły"
    why: "Liczba pokazuje, co się zepsuło, a transkrypt — dlaczego. Czasem myli się nie bot, tylko sam oceniający."
hint: "Najpierw „co znaczy dobrze”, potem testy, potem pomiar wyjściowy, następnie poprawka i analiza porażek."
:::

question: "Paweł chce, żeby bot już nigdy nie zaczął mylić cen po kolejnej poprawce. Jakiego zestawu potrzebuje?"
options:
  - text: "Regression eval: zadania, które bot już rozwiązuje, a odsetek zaliczeń ma się trzymać blisko 100%"
    correct: true
    why: "Regression eval odpowiada na pytanie „czy bot nadal robi to, co umiał?”. Każdy spadek poniżej 100% to sygnał, że poprawka coś zepsuła."
  - text: "Capability eval: nowe trudne zadania, z którymi bot na razie radzi sobie w 30% przypadków"
    correct: false
    why: "Capability eval służy do rozwoju: zaczyna się od niskiego odsetka. Żeby nie zepsuć tego, co działa, potrzebny jest inny zestaw."
  - text: "Sprawdzać ręcznie trzy pytania po każdej poprawce"
    correct: false
    why: "Właśnie tak Paweł przegapił błąd z cenami. Trzy pytania nie obejmują nawet głównych scenariuszy."
  - text: "Poprosić bota, żeby sam powiedział, czy jest lepszy"
    correct: false
    why: "To nie jest pomiar. Potrzebne są stałe zadania i niezależny oceniający; dokumentacja radzi nawet oceniać innym modelem niż ten, który odpowiada."
hint: "Jeden rodzaj evals pomaga się rozwijać, drugi chroni przed cofnięciem się. Którego potrzeba tutaj?"
:::

::: step explain
Model oceniający to też prompt. Według dokumentacji dobry oceniający potrzebuje:

- szczegółowej, jasnej rubryki;
- konkretnego wyniku: „correct” albo „incorrect” lub skali 1–5;
- rozumowania przed oceną.

Do tego lepiej oceniać innym modelem niż ten, który odpowiadał. Napisz taki prompt sam.
:::

::: step summary
**Każda poprawka promptu przechodzi przez ten sam zestaw testów.**

Zacznij od 20–50 zadań z prawdziwych awarii i przypadków brzegowych. Kod do jednoznacznych spraw, model z rubryką do sensu i tonu, człowiek do spornych. I czytaj transkrypty porażek.
:::
