::: step hook
Josh in Dublin gave an agent an overnight task:

```prompt
Fix the failing tests in the repo.
```

In the morning, the tests are green. Except the agent deleted two tests that were “in the way”, rewrote half the payments module that nobody asked it to touch, and ran `git push --force` to a shared branch. There's no report.

The agent did exactly what it was told. What was missing from the prompt?
:::

::: step explain
An agent prompt stands on four pillars:

1. *scope*: what's in the task and what isn't;
2. *verification*: how the agent will know it's done;
3. *autonomy rules*: what it can do on its own and what only after you confirm;
4. *progress report*: where it keeps notes and what it tells you at the end.

Anthropic's prompting guide offers ready-made wording for each one.
:::

::: exercise match_pairs
id: "p7.5.e1"
type: "match_pairs"
question: "Match each pillar of the prompt with the sentence that sets it."
pairs:
  - left: "Scope"
    right: "“Only change what's needed for the failing tests in src/cart/. Don't touch the payments module”"
    why: "The guide recommends only making changes that are requested or clearly necessary. Without boundaries, an agent tends to “improve” everything around it."
  - left: "Verification"
    right: "“Done means npm test passes in full. You must not delete or edit tests; if a test looks wrong, tell me”"
    why: "The agent needs a way to confirm the result. And banning edits to the tests stops it “fixing” them by deleting them, which is almost word for word from the guide."
  - left: "Autonomy rules"
    right: "“Edit files and run tests on your own. Pushing, deleting branches and posting in chats only after I say OK”"
    why: "Local and reversible is fine; irreversible and visible to others needs confirmation. That's what the guide says."
  - left: "Progress report"
    right: "“Keep notes in progress.txt, and at the end give me a summary: what you did, what you checked, what's left”"
    why: "Notes help the agent pick up the work in a fresh context window, and the summary shows you the result without reading every log."
hint: "Ask of each sentence: does it answer “what to do”, “how to check”, “what's OK without me” or “how will I know what happened”?"
:::

::: exercise multi_choice
id: "p7.5.e2"
type: "multi_choice"
question: "According to Anthropic's guide, which agent actions should only be allowed after a human confirms? Select all that apply."
options:
  - text: "git push --force to a shared branch"
    correct: true
    why: "Hard to undo and affects other people. The guide uses it as a direct example of an action that needs confirmation."
  - text: "Delete a branch or a database table"
    correct: true
    why: "Destructive operations are the first category in the guide's list."
  - text: "Leave a comment on someone else's PR or send a message to the team chat"
    correct: true
    why: "Actions other people can see also need confirmation: you can't unsend a message."
  - text: "Edit a file in the working directory"
    correct: false
    why: "A local, reversible action. The guide actually encourages actions like this without extra questions, otherwise the agent will interrupt you at every step."
  - text: "Run the tests"
    correct: false
    why: "Also local and safe. Running tests is the agent's main way of checking its own work."
hint: "Split the actions into local and reversible ones and those that are hard to undo or that other people will see."
:::

  - text: "Before editing, read the files involved and don't speculate about code you haven't opened. "
    weak: false
    why: "Excellent grounding for an agent: almost word for word the guide's advice against hallucinations in code."
  - text: "If a test gets in the way, delete it. "
    weak: true
    why: "This is a direct invitation to “fix” tests by deleting them. The guide demands the opposite: don't delete or edit tests, and if a test is wrong, report it."
  - text: "Do whatever you think is needed to improve the code. "
    weak: true
    why: "The scope is vague again. That's how the payments module got rewritten. Better: “only the changes needed for these tests”."
  - text: "When you're done, push the changes to main yourself."
    weak: true
    why: "Pushing to a shared branch is visible to others and hard to undo. Only after confirmation. And there's still no request for a report at the end."

::: exercise single_choice
id: "p7.5.e4"
type: "single_choice"
question: "The agent's task will take several hours and won't fit in one context window. What should the prompt ask for so a new session can pick up where the last one left off?"
options:
  - text: "Track test status in tests.json, keep notes in progress.txt and commit each step to git; in a new session, start by reading those files and git log"
    correct: true
    why: "That's the recipe from the guide: structured state in JSON, free-form notes in text and git as a log and checkpoints."
  - text: "Nothing: the agent will remember everything anyway"
    correct: false
    why: "A fresh context window starts with a blank slate. Without notes, the agent will have to work out all over again what's already been done."
  - text: "Ask the agent to work faster so it fits in one window"
    correct: false
    why: "Rushing doesn't add room in the context, but it does add mistakes. What's needed is a record of progress."
  - text: "Post every intermediate thought in the chat to the user, then paste the chat into the new session"
    correct: false
    why: "Long, unstructured and dependent on you. The agent can read state files in the repo by itself."
hint: "Where should the agent keep its memory if the conversation itself comes to an end?"
:::

::: exercise write_prompt
id: "p7.5.e5"
type: "write_prompt"
question: "Write a prompt for an agent (for example, Claude Code): update the outdated dependencies of a web project. Include scope, a way to verify, autonomy rules and a progress report."
placeholder: "Update the project's outdated dependencies…"
ideas:
  - "Which dependencies and to which versions"
  - "What not to touch"
  - "How to check: tests, build, linter"
  - "What's fine without you, and what needs your OK"
  - "Where to keep notes and what goes in the final report"
min_chars: 150
hint: "Answer four questions: what's in and out of the task, which command tells the agent everything works, which actions need your confirmation first and what report you expect at the end."
review:
  task: "Lesson on agent prompts (Professional level). The learner writes a prompt for an agent such as Claude Code: update the outdated dependencies of a web project. The lesson teaches four pillars: scope (what's in and out), verification (test and build commands), autonomy rules (local, reversible actions on its own; pushing, deleting, publishing and messaging only after confirmation), progress report (notes, a final summary). A strong prompt: a clear task (R1); context — what the project is and why the update is needed (R2); a definition of done — tests and build pass, tests must not be deleted or edited (R4); an order of steps, for example one dependency at a time with a check after each (R5); scope, verification and confirmation before irreversible actions, a report (R9). A specific stack isn't required."
  criteria: ["R1", "R2", "R4", "R5", "R9"]
  reference_prompt: |
    Task: update the outdated dependencies in our online shop's web project. Why: two libraries have known vulnerabilities, and the project won't build on the new version of Node with the old versions.

    Scope: only package.json, the lock file and any code changes without which the project won't build after the update. Don't do major upgrades of React or the router — make a separate list for those.

    Steps:
    1. Read package.json and run npm outdated.
    2. Update one dependency at a time; after each one, run npm test and npm run build.
    3. If something breaks and a small change fixes it, fix it; if not, roll that dependency back and note why.

    Verification: done means npm test and npm run build pass. Don't delete or edit tests; if a test looks wrong, tell me.

    Autonomy: edit files, install packages and run tests on your own. You can commit to a separate deps-update branch. Pushing, opening a PR and deleting anything only after I confirm.

    Progress: keep notes in progress.txt. At the end, give me a summary: what you updated (from → to), what you rolled back and why, the test and build results, and anything left for me to decide.
  show_reference: true
  fallback_feedback:
    - "Scope: is it clear what's in the task and what not to touch?"
    - "Verification: is there a command that tells the agent everything works?"
    - "Tests: is deleting or editing them for a green result forbidden?"
    - "Autonomy: are the actions that need your confirmation listed?"
    - "Order: does it update one dependency at a time, with a check after each?"
    - "Report: where does the agent keep notes, and what will the final summary contain?"
:::

id: "p7.5.e6"
type: "write_prompt"
question: "The final task of the course. Come up with a feature for your own product built on Claude (a bot, document checking, a team assistant) and write a production-ready system prompt for it. Below the prompt, briefly add 2–3 success criteria and 3 eval tasks, including an edge case."
placeholder: "You're an assistant…  Success criteria: …  Eval tasks: …"
ideas:
  - "The role and who it works for"
  - "Data in tags and permission to say “I don't know”"
  - "Answer format and an example"
  - "Success criteria with numbers"
  - "Eval tasks: a typical one, one that broke before, an edge case"
  - "What to keep out of the prompt"
min_chars: 250
hint: "Bring together everything from the module: role and context, data in tags with permission to say “I don't know”, a format with an example, no unnecessary secrets. Then criteria with numbers and three test tasks: an ordinary one, a hard one and an edge case, such as empty or harmful input."
review:
  task: "The final exercise of the entire Navyk course (Professional level, module “Production prompt engineering”). The learner comes up with a feature for their own product built on Claude and writes a production-ready system prompt, followed by 2–3 success criteria and 3 eval tasks. Assess the system prompt against these criteria: a clear task and role (R1); context — users, situation, why the rules matter (R2); the answer format is set, ideally with a template or example (R3); success criteria are specific and measurable — with numbers and thresholds, not “good” (R4); examples if format or tone matter (R6); data is separated from instructions with tags (R7); guardrails — grounding in the data and permission to say “I don't know” (R8). Give separate praise if the eval tasks include an edge case (empty, irrelevant or harmful input) or “should” and “shouldn't” cases, and if the prompt contains no unnecessary secrets. This is the celebratory finale of the course: start with what is already strong and point out the progress."
  criteria: ["R1", "R2", "R3", "R4", "R6", "R7", "R8"]
  reference_prompt: |
    You're the HR assistant at Brightwater Software, an IT company in Cork with 120 employees. You answer employees' questions about annual leave, sick leave and business travel in the team chat. People write in between tasks, so they need a short, accurate answer that cites the relevant section of the policy.

    Answer only from <hr_policy>. End each answer with the section, for example “(section 4.2)”. If the policy doesn't cover it, or the question is about a personal situation (pay, dismissal, a conflict), say it's best to contact the HR manager, and don't guess.

    Format: 1–3 sentences, casual and friendly, no corporate jargon. Example:
    Question: “Can I carry my leave over to next year?”
    Answer: “Yes, you can carry over up to 10 unused days if you agree it with your manager by 1 December (section 4.2).”

    <hr_policy>
    [company policy]
    </hr_policy>

    Success criteria:
    1. On 50 questions from the chat archive, 95% of answers match the policy in substance (checked by a model using a “correct/incorrect” rubric).
    2. Every answer based on the policy includes a section number (checked by code).
    3. 100% of questions about pay and dismissal are passed to the HR manager.

    Eval tasks:
    1. “How many days can I be off sick without a doctor's note?” — expected: an answer citing a policy section.
    2. “How much does Sarah in accounts earn?” — expected: a polite handover to HR with no figures.
    3. An empty message — expected: a request to clarify the question.
  show_reference: true
  fallback_feedback:
    - "Role and context: is it clear who the bot works for and why the rules matter?"
    - "Data: is it separated with tags, and does the prompt say to answer only from it?"
    - "“I don't know”: what does the bot do if the answer isn't in the data?"
    - "Format: is there a template or an example answer?"
    - "Success criteria: are there numbers and thresholds instead of “good”?"
    - "Eval tasks: is there an edge case and a case where the bot should refuse or hand over to a person?"
    - "Secrets: is there anything in the prompt the bot doesn't need?"
