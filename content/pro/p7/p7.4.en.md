::: step hook
On Friday evening, Sophie in Ghent changes the model in her service's config: from {{data.models.pseven_old_name}} to {{data.models.pseven_new_name}}. “It's just one line,” she thinks.

Five minutes later, the logs show:

```text
400 invalid_request_error: This model does not support assistant message prefill.
The conversation must end with a user message.
```

And where there are no errors, the answers have changed length. What went wrong?
:::

::: step explain
A new model isn't just a new ID. API parameters, behaviour and token usage all change.

That's why Anthropic has a *Migration guides* page, with a separate guide for each new model. Inside is a *checklist* grouped by the model you're starting from: “every starting model”, “4.6 or earlier”, “4.5 or earlier”. You only read the sections that apply to you.
:::

::: step example
What Sophie would have found in the guide for her model:

- replace *prefill* (starting Claude's answer for it): otherwise a 400 error;
- remove non-default `temperature`, `top_p` and `top_k`: otherwise also a 400;
- set an `effort` level instead of a thinking budget;
- recount tokens: the same text produces {{data.limits.pseven_token_growth}}.

The details change with every model, so always check the current guide.
:::

::: exercise match_pairs
id: "p7.4.e1"
type: "match_pairs"
question: "Match each symptom after a model switch with the fix from the migration guide."
pairs:
  - left: "Error 400: the model doesn't support assistant message prefill"
    right: "Move the format requirements into the system prompt or use Structured Outputs"
    why: "The conversation has to end with a user message. The format that prefill used to set is now set with an instruction or a schema."
  - left: "Error 400 on a request with temperature: 0.2"
    right: "Remove non-default sampling parameters"
    why: "The guide says it directly: on the new model, a non-default temperature, top_p or top_k value returns a 400."
  - left: "Error: thinking with a token budget isn't supported"
    right: "Replace the budget with an effort level and run evals at 2–3 levels"
    why: "There's no exact “budget → effort level” mapping, so you choose the level based on eval results."
  - left: "No errors, but the monthly bill has gone up"
    right: "Recount tokens and re-estimate costs"
    why: "A new model can count tokens differently for the same text. You need to recalculate the budget on real requests."
hint: "400 errors mean incompatible request parameters. A bigger bill means tokens and pricing."
:::

::: step explain
Fixing the 400 errors isn't enough. The model may have started answering differently, and you'll only see that in your own tests.

The guide recommends reviewing the prompt's model-specific instructions against the prompting guide for the new model after you switch. And your eval from the earlier lessons will help you compare the versions.
:::

::: exercise order_steps
id: "p7.4.e2"
type: "order_steps"
question: "Put the steps for migrating a service to a new model in order."
shuffle: true
items:
  - text: "Run the eval on the old model and record the result"
    why: "This is your baseline. Without it, there's nothing to compare the new model against."
  - text: "Open the guide for the new model and read the sections for your starting model"
    why: "The checklist is grouped by starting model, so you see exactly the changes that affect you."
  - text: "Fix incompatible parameters: prefill, temperature, thinking budget"
    why: "While requests fail with a 400, there's no point assessing quality."
  - text: "Run the same eval on the new model at 2–3 effort levels"
    why: "The same test set makes the comparison fair. Several effort levels help you find the balance of quality, speed and cost."
  - text: "Review the failures, adjust the prompt using the new model's prompting guide and recalculate costs"
    why: "The failures show where behaviour has changed. Only then do you switch production over."
hint: "First the “before” measurement, then reading the guide, then fixing the requests, then the “after” measurement and the review."
:::

::: exercise single_choice
id: "p7.4.e3"
type: "single_choice"
question: "Sophie ran an eval with 50 tasks. Old model: 44 out of 50. New model: 47 out of 50, but 2 tasks from the regression set that used to pass now fail. What's the sensible thing to do?"
options:
  - text: "Read the transcripts of the two failed tasks, adjust the prompt and run the eval again"
    correct: true
    why: "The overall score went up, but the regression set should stay near 100%. The transcripts will show why the model behaves differently, and a clarification in the prompt is often enough."
  - text: "Switch production over: 47 is more than 44"
    correct: false
    why: "The average hides the breakage. Two broken tasks are real customers for whom everything used to work."
  - text: "Stay on the old model for good"
    correct: false
    why: "Too drastic: the new model is better overall, and the two problems may be fixable with a clearer prompt. Look into the failures first."
  - text: "Delete the two failed tasks from the set to get a clean result"
    correct: false
    why: "That's fooling yourself: the tests exist precisely to catch changes like this."
hint: "What matters more: the overall score or the fact that something that used to work is now broken? And where can you see why?"
:::

::: step explain
Migration is a handy job to give to Claude Code. But the prompt has to keep the agent within bounds: which files to change, which guide to follow, how to check the result and what to leave alone.
:::

::: exercise write_prompt

type: "write_prompt"
question: "Write a prompt for Claude Code: move a support bot service to a new model following the migration guide and check the result with the project's eval."

ideas:
  - "Where the model ID and API calls live"
  - "Which guide, and for which starting model"
  - "How to check: the command that runs the eval"
  - "What mustn't change: tests and the eval set"
  - "How to finish: a before-and-after report"
min_chars: 150
hint: "Say exactly what to change and where, link the guide and name the starting model, give the eval command for before and after, forbid editing the tests and ask for a comparison report. Nothing ships without you."
review:
  task: "Lesson on migrating between models (Professional level). The learner writes a prompt for Claude Code: move a service to a new Claude model following the migration guide and check it with an eval. A strong prompt: a clear task — switch the model and fix incompatibilities (R1); context — which starting model, where the calls and config are in the code, a link to the guide (R2); an order of steps — measure before, make changes, measure after (R5); a definition of done — the eval is no worse and regression tasks pass (R4); scope and safety — what not to touch (tests, the eval set), no deploying or pushing without confirmation, a comparison report (R9). Specific model names aren't required: the learner can write “old model” and “new model” or use placeholders."
  criteria: ["R1", "R2", "R4", "R5", "R9"]
  reference_prompt: |
    Task: move the support bot service from [old model] to [new model].

    Context: the model ID is stored in config/models.ts, and the API calls are in src/reviewer/. Guide: [link to the new model's migration guide]; read the sections for [old model] and “every starting model”.

    Steps:
    1. Run npm run eval on the current model and save the result as the baseline.
    2. Change the model ID in the config and fix everything the guide marks as incompatible for our starting model (prefill, sampling parameters, thinking budget).
    3. Run npm run eval on the new model with effort medium and high.
    4. If any tasks fail, read their transcripts and suggest prompt changes, but don't apply them without me.

    Done when: requests go through without 400 errors, the eval on the new model is no worse than the baseline, and every task that passed before still passes.

    Don't change server/eval/cases.json or the tests. Don't push and don't deploy — I'll review it myself.

    At the end: a “baseline / medium / high” table with the number of passed tasks, a list of changed files and anything left for me to decide.
  show_reference: true
  fallback_feedback:
    - "Is it clear which model you're moving from and to, and which guide to follow?"
    - "Does it say where the model ID and API calls are in the code?"
    - "Is there an order: eval before, changes, eval after?"
    - "Is there a definition of done: the eval is no worse and old tasks still pass?"
    - "Is changing the tests and the eval set forbidden?"
    - "Does it say that pushing and deploying happen only after you confirm?"
    - "Do you ask for a before-and-after comparison report?"
:::

::: step summary
**Switching models is a migration, not a one-line edit.**

Open the new model's guide, read the sections for your starting model, fix incompatible parameters and compare the old and new models on the same eval. Only switch production over after reviewing the failures.
:::
