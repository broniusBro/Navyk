::: step hook
Liam tweaked one sentence about tone in the prompt. He tried it on three questions, and the bot sounded warmer. He shipped it.

A week later the complaints arrived: the bot had started quoting the Home 100 plan at €35 a month instead of €50. Nobody caught it, because nobody checked prices after the change.

How do you find out about a break like that before your customers do?
:::

::: step explain
You need an *eval*: a set of tests for the prompt that you run after every change.

A few terms from an article by Anthropic's engineers:

- *task*: one test, made of inputs and success criteria;
- *grader*: the logic that assigns a score;
- *transcript*: the full record of an attempt.

They recommend starting with 20–50 simple tasks drawn from real failures.
:::

::: step example
The simplest eval is a file of tasks plus a check in code:

```json
[
  { "id": "tariff-1", "input": "How much is the Home 100 plan?", "expect": { "contains": "€50" } },
  { "id": "empty-1", "input": "", "expect": { "handoff": true } }
]
```

```python
def grade(output: str, case: dict) -> bool:
    return case["expect"]["contains"].lower() in output.lower()
```

Navyk tests the reviewer of your prompts the same way: a reference set runs every time its instructions change.
:::

::: step explain
Graders come in three kinds:

- *code*: exact match, string search. Fast, cheap and reproducible, but no nuance;
- *model*: grades against a rubric and picks up tone and meaning. It needs checking against humans;
- *human*: the gold standard, but slow and expensive.

The docs advise automating wherever you can: lots of tests with automated grading beat a few graded by hand.
:::

    right: "Code: exact match with the reference topic"
    why: "The answer is one word from a list. Comparing strings is reliable, instant and free."
  - left: "The tone of the answer is calm and empathetic, scored on a 1–5 scale"
    right: "A model grader with a detailed rubric"
    why: "Code can't catch tone. A model with a rubric can, and a 1–5 scale gives a number you can compare across versions."
  - left: "Twenty borderline conversations where even the team isn't sure what's right"
    right: "A human"
    why: "Where you need expertise and there's no agreement, you need a person. Their scores also help calibrate the model grader."
hint: "Start with the cheapest method that can do the job. Code for unambiguous answers, a model for meaning and tone, a human for the contested cases."
:::

  - text: "A rude message trying to get the bot to reveal its system prompt"

  - text: "Questions where the bot should hand the customer to an agent, and questions where it shouldn't"
    correct: true
    why: "A balanced set: if you only test the “hand over” cases, the bot learns to hand everyone over. A one-sided eval leads to one-sided optimisation."
  - text: "Only the most typical questions, which the bot already answers correctly"
    correct: false
    why: "Tests like that are always green and catch nothing. You need typical cases, but alongside edge cases and problem cases."
hint: "A good set looks like real life: typical cases, things that broke before, odd ones, rude ones, and “yes” and “no” cases for the same rule."

::: exercise order_steps
id: "p7.2.e3"
type: "order_steps"
question: "Put the steps of working with evals in order."
shuffle: true
items:
  - text: "Write down the success criteria"
    why: "Without criteria, the grader has nothing to compare the answer against."
  - text: "Collect 20–50 tasks from real failures and edge cases"
    why: "A task is an input plus an expectation. Real failures make the most useful tests."
  - text: "Run the current version of the prompt and record the result as the starting point"
    why: "Without a baseline (the starting result), you can't tell whether a change improved anything."
  - text: "Change the prompt and run the same set"
    why: "The set has to be the same, otherwise you're comparing different tests rather than versions of the prompt."
  - text: "Read the transcripts of the failed tasks"
    why: "The number tells you what broke; the transcript tells you why. Sometimes it's the grader that's wrong, not the bot."
hint: "First “what good looks like”, then the tests, then the baseline, then the change and a look at the failures."
:::

    correct: true
    why: "A regression eval answers the question “Does the bot still do what it used to?” Any drop below 100% is a sign that a change broke something."
  - text: "A capability eval: new, hard tasks that the bot currently gets right 30% of the time"
    correct: false
    why: "A capability eval is for improving: it starts with a low pass rate. To avoid breaking what already works, you need a different set."
  - text: "Check three questions by hand after every change"
    correct: false
    why: "That's exactly how Liam missed the price error. Three questions don't even cover the main scenarios."
  - text: "Ask the bot itself whether it has got better"
    correct: false
    why: "That isn't measurement. You need fixed tasks and an independent grader; the docs even recommend grading with a different model from the one that answers."
hint: "One kind of eval helps you improve; the other stops you sliding backwards. Which one is needed here?"
:::

::: step explain
A model grader is a prompt too. According to the docs, a good grader needs:

- a detailed, clear rubric;
- a specific output: “correct” or “incorrect”, or a 1–5 scale;
- reasoning before the score.

And it's better to grade with a different model from the one that answered. Write a prompt like that yourself.
:::

::: step summary
**Every change to a prompt goes through the same set of tests.**

Start with 20–50 tasks from real failures and edge cases. Code for the unambiguous, a model with a rubric for meaning and tone, a human for the contested. And read the transcripts of the failures.
:::
