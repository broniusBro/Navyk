::: step hook
Tom wrapped his CRM's API in an MCP server: 30 tools, one per endpoint.

Claude gets confused. To find a customer, it calls `list_contacts`, gets all 5,000 contacts, and the context fills up. Then it calls `get` with a `user` parameter and passes a name instead of an ID.

The server works, but the agent struggles with it. Let's see how to fix that.
:::

::: step explain
A tool isn't a wrapper around an API endpoint; it's an action shaped around the agent's task.

- Instead of `list_contacts`, which returns everyone, build `search_contacts`: the agent needs one customer, not thousands.
- Instead of three calls (“find a free slot, check attendees, create the meeting”), offer one `schedule_event` that does it all.

More tools doesn't mean better.
:::

::: exercise single_choice
id: "p5.6.e1"
type: "single_choice"
question: "A user asks: “Tell Natalie at Alpha Build that the contract is ready.” Which set of tools will help the agent most?"
options:
  - text: "search_contacts(query) and message_contact(contact_id, text)"
    correct: true
    why: "Yes. The agent finds the right person with a search and messages them straight away. It's an exact fit for the task, with no dump of the whole database."
  - text: "list_contacts() with no parameters and send_message(raw_payload)"
    correct: false
    why: "list_contacts will dump the whole database into the context, and raw_payload forces Claude to guess the API request format. That way the agent burns tokens and makes mistakes."
  - text: "30 tools, one for each CRM endpoint"
    correct: false
    why: "The more similar tools there are, the harder it is to pick the right one. Anthropic's article says outright that more tools isn't always better."
  - text: "A single do_anything(command) tool that accepts any command"
    correct: false
    why: "The agent won't understand what it can do or in what format. The description will be vague, and errors will be hard to fix."
hint: "What does the agent need for this task: the whole database or one person, plus a way to message them?"
:::

::: step explain
Names and parameters:

- Group tools with a service prefix: `asana_search`, `jira_search`. That way they can't be confused if two servers each have their own `search`.
- Name parameters unambiguously: `user_id`, not `user`.

Write the description as if you were explaining the job to a new colleague: what the tool does, when to use it, what the parameters mean, what it returns and what it can't do. It's a prompt like any other.
:::

::: step example
According to Anthropic, precise refinements to *tool descriptions* helped Claude Sonnet 3.5 reach state-of-the-art results on the SWE-bench Verified benchmark, with noticeably fewer errors.

The model was the same. Only the text it uses to choose and call tools had changed.
:::

::: exercise find_error
id: "p5.6.e2"
type: "find_error"
question: "Here's a tool description from Tom's server. Tap every fragment where Claude would stumble."
prompt: "get: Gets data. Param user: the user. Returns everything about the user in JSON. Use for CRM tasks."
segments:
  - text: "get: "
    weak: true
    why: "The name get says nothing, and a tool on another server could have the same name. Better: crm_get_contact."
  - text: "Gets data. "
    weak: true
    why: "What data? The description should be specific: “Returns a CRM contact card by its ID”."
  - text: "Param user: the user. "
    weak: true
    why: "It's unclear what to pass: a name, an email or an ID. That's exactly the mistake from Tom's story. Use user_id and give the format with an example."
  - text: "Returns everything about the user in JSON. "
    weak: true
    why: "“Everything” means lots of tokens and little value. Better to return the essentials: name, company, phone, latest deal, with details on request."
  - text: "Use for CRM tasks."
    weak: true
    why: "Too general: all 30 tools fit “CRM tasks”. Say exactly when to call this one, for example “when the contact ID is already known; to search by name, use crm_search_contacts”."
hint: "Read the description through a new colleague's eyes: what does the tool do, what do you pass, what do you get back, and when do you use it?"
:::

::: step explain
The model reads the tool's response too, and every token takes up its context. So:

- return the essentials, not everything, and readable names instead of UUIDs;
- offer a choice of detail, such as a `response_format` parameter with `concise` and `detailed` values;
- use pagination, filters and sensible default limits.

Claude Code warns about output over {{data.limits.pfive_cc_output_warn}} and by default truncates it at {{data.limits.pfive_cc_output_max}}. In claude.ai and Desktop, the result limit is {{data.limits.pfive_web_result_max}}.
:::

::: step explain
An error is a hint for the agent too. The server returns an execution error in the result with `isError: true` and clear text. Then Claude can correct itself.

Bad: `Error 400`.

Good, as in the specification: `Invalid departure date: must be in the future. Current date is 08/08/2025.`

A good message says what's wrong and how to fix it.
:::

The description is a prompt for Claude: the model uses it to decide when to call the tool and how to fill in the parameters. A strong description: it's clear what the tool does and when to call it, and when not to (R1); every parameter is explained unambiguously — what query is, the allowed values for status, the default and maximum for limit (R2); it says what the tool returns and in what form, ideally concise and with readable names instead of IDs (R3); it describes what counts as a successful call and what to do with an empty result or an overly broad query (R4).   criteria: ["R1", "R2", "R3", "R4"]
  reference_prompt: |
    Search CRM deals by deal name or company name. Use this when the user mentions a deal or a client company and you need its status, amount or owner. To read one deal in full when you already have its ID, use crm_get_deal instead.

        query: Part of the deal name or company name, e.g. "Alpha Build" or "Dublin warehouse". Case-insensitive.
        status: Optional filter: "open", "won" or "lost". Omit to search all deals.

  show_reference: true

    - "Does it say when to call it and when to use a different tool?"

    - "Does it describe what the tool returns: which fields, with readable names rather than just IDs?"
    - "Does it say what happens with an empty result or too many matches?"

::: step summary
**A good tool performs an action shaped around the agent's task; it doesn't just mirror an API endpoint.**

A name with a service prefix, unambiguous parameters, a description written as if for a new colleague, a short response with readable names, and an error that suggests the fix.

You've finished the MCP module: you know the architecture, primitives and transports, you've built your own server, and you can connect it to Claude.
:::
