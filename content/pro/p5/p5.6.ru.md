::: step hook
Олег завернул API своей CRM в MCP-сервер: 30 инструментов, по одному на каждый эндпоинт.

Claude путается. Чтобы найти клиента, он вызывает `list_contacts`, получает все 5000 контактов, и контекст забивается. Потом вызывает `get` с параметром `user` и передаёт имя вместо ID.

Сервер работает, а агенту с ним плохо. Разберёмся, как это исправить.
:::

::: step explain
Инструмент — это не обёртка над эндпоинтом API, а действие под задачу агента.

- Вместо `list_contacts`, который отдаёт всех, сделай `search_contacts`: агенту нужен один клиент, а не тысячи.
- Вместо трёх вызовов «найти свободное время, проверить участников, создать встречу» — один `schedule_event`, который сделает всё сам.

Больше инструментов не значит лучше.
:::

  - text: "30 инструментов, по одному на каждый эндпоинт CRM"
    correct: false
    why: "Чем больше похожих инструментов, тем труднее выбрать нужный. Статья Anthropic прямо говорит, что больше инструментов не всегда лучше."
  - text: "Один инструмент do_anything(command), который принимает любую команду"
    correct: false
    why: "Агент не поймёт, что можно делать и в каком формате. Описание будет расплывчатым, а ошибки трудно исправлять."
hint: "Что нужно агенту для этой задачи: вся база или один человек, плюс способ ему написать?"
:::

::: step explain
Имя и параметры:

- Группируй инструменты префиксом сервиса: `asana_search`, `jira_search`. Так их не спутать, если у двух серверов есть свой `search`.
- Называй параметры однозначно: `user_id`, а не `user`.

Описание пиши так, будто объясняешь задачу новому сотруднику: что делает инструмент, когда его брать, что значат параметры, что он вернёт и чего не умеет. Это такой же промпт, как любой другой.
:::

::: step example
По данным Anthropic, точные правки *описаний инструментов* помогли Claude Sonnet 3.5 выйти на лучший результат в бенчмарке SWE-bench Verified: ошибок стало заметно меньше.

Модель была та же. Поменялись только тексты, по которым она выбирает и вызывает инструменты.
:::

::: exercise find_error
id: "p5.6.e2"
type: "find_error"
question: "Это описание инструмента в сервере Олега. Нажми на все фрагменты, на которых Claude споткнётся."
prompt: "get: Gets data. Param user: the user. Returns everything about the user in JSON. Use for CRM tasks."
segments:
  - text: "get: "
    weak: true
    why: "Имя get ничего не говорит, и с таким же именем может быть инструмент на другом сервере. Лучше crm_get_contact."
  - text: "Gets data. "
    weak: true
    why: "Какие данные? Описание должно сказать конкретно: «Возвращает карточку контакта CRM по его ID»."
  - text: "Param user: the user. "
    weak: true
    why: "Неясно, что передавать: имя, email или ID. Отсюда ошибка из истории Олега. Нужно user_id и формат с примером."
  - text: "Returns everything about the user in JSON. "
    weak: true
    why: "«Всё» — значит, много токенов и мало пользы. Лучше вернуть главное: имя, компанию, телефон, последнюю сделку, а подробности давать по запросу."
  - text: "Use for CRM tasks."
    weak: true
    why: "Слишком общо: под «задачи CRM» подходят все 30 инструментов. Скажи, когда именно звать этот, например «когда ID контакта уже известен; для поиска по имени используй crm_search_contacts»."
hint: "Прочитай описание глазами нового сотрудника: что делает инструмент, что передать, что получишь и когда его брать?"
:::

::: step explain
Ответ инструмента тоже читает модель, и каждый токен занимает её контекст. Поэтому:

- возвращай главное, а не всё, и понятные имена вместо UUID;
- дай выбор подробности, например параметр `response_format` со значениями `concise` и `detailed`;
- используй пагинацию, фильтры и разумные лимиты по умолчанию.

Claude Code предупреждает о выводе больше {{data.limits.pfive_cc_output_warn}} и по умолчанию обрезает его на {{data.limits.pfive_cc_output_max}}. В claude.ai и Desktop предел результата — {{data.limits.pfive_web_result_max}}.
:::

::: step explain
Ошибка — тоже подсказка для агента. Ошибку выполнения сервер возвращает в результате с `isError: true` и понятным текстом. Тогда Claude сможет исправиться сам.

Плохо: `Error 400`.

Хорошо, как в спецификации: `Invalid departure date: must be in the future. Current date is 08/08/2025.`

Хорошее сообщение говорит, что не так и как исправить.
:::

    right: "Ответ: «Сделка «Склад Львов», ответственный Ирина Коваль»"

  - left: "Ошибка: «Error 400»"
    right: "Ошибка: «Дата должна быть в будущем. Сегодня 14.10.2026, формат YYYY-MM-DD»"
    why: "Конкретное сообщение показывает, что исправить. Claude повторит вызов правильно, а не сдастся."
  - left: "Два сервера, у каждого инструмент search"
    right: "Инструменты jira_search и asana_search"
    why: "Префикс сервиса разделяет похожие инструменты, и Claude не перепутает, где искать."

:::

::: step summary
**Хороший инструмент делает действие под задачу агента, а не повторяет эндпоинт API.**

Имя с префиксом сервиса, однозначные параметры, описание как для нового сотрудника, короткий ответ с понятными именами и ошибка, которая подсказывает исправление.

Модуль MCP пройден: ты знаешь архитектуру, примитивы и транспорты, собрал свой сервер и умеешь подключать его к Claude.
:::
