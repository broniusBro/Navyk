::: step hook
Michał z Lublina w jednym terminalu poprosił Claude o nowy formularz logowania, a w drugim — o naprawienie błędu w koszyku. Po dziesięciu minutach obie sesje edytowały ten sam `package.json`, a testy padały przez cudze zmiany.

Dwie sesje — dobry pomysł. Jeden folder na dwie — zły.
:::

::: step explain
Rozwiązanie to *git worktree*: osobny folder roboczy z własnymi plikami i własną gałęzią, ale ze wspólną historią repozytorium. Jak dwa stoły w jednym warsztacie: narzędzia wspólne, a obrabiane elementy sobie nie przeszkadzają.

```bash
claude --worktree feature-auth
```

Claude utworzy folder `.claude/worktrees/feature-auth/` na nowej gałęzi `worktree-feature-auth`. Druga sesja — to samo polecenie z inną nazwą w innym terminalu.
:::

::: step explain
Trzy praktyczne drobiazgi:

- dodaj `.claude/worktrees/` do `.gitignore`, żeby foldery nie zaśmiecały głównej kopii;
- worktree to świeża kopia, więc zależności instaluje się od nowa, a pliki takie jak `.env` przenosi `.worktreeinclude`;
- przy wyjściu pusty worktree bez nazwy usuwa się sam. Jeśli są w nim zmiany, Claude zapyta, czy go zachować, czy usunąć.
:::

::: step explain
Gdy sesji jest dużo, wygodnie mieć je na jednym ekranie. To *agent view*, status: {{data.plans.pthree_agent_view_status}}.

```bash
claude agents
claude --bg "ustal, dlaczego nie przechodzi test SettingsChangeDetector"
```

Każdy prompt uruchamia sesję w tle. Przed edycją plików przenosi się ona do własnego worktree. Statusy Working, Needs input, Completed i inne — od razu widać, kto czeka na ciebie.
:::

::: step explain
Równoległość przydaje się nie tylko dla szybkości. Sesja, która właśnie napisała kod, jest skłonna uważać go za dobry. Świeży kontekst patrzy uczciwiej.

To wzorzec *„autor/recenzent”*: sesja A pisze, sesja B bez historii A robi review, A poprawia według uwag. Podobny wariant: jeden Claude pisze testy, drugi — kod, który je przechodzi.
:::

::: exercise order_steps
id: "p3.6.e4"
type: "order_steps"
question: "Ułóż kroki wzorca „autor/recenzent” we właściwej kolejności."
shuffle: true
items:
  - text: "Sesja A implementuje ograniczenie liczby żądań do API"
    why: "Autor wykonuje zadanie jak zwykle, we własnym worktree."
  - text: "Sesja B ze świeżym kontekstem sprawdza kod A według kryteriów: przypadki brzegowe, wyścigi, zgodność ze stylem projektu"
    why: "Recenzent nie widzi rozumowania autora i ocenia tylko wynik. Dlatego zauważa to, co autor uważał za oczywiste."
  - text: "Uwagi B trafiają do sesji A"
    why: "Review bez przekazania niczego nie zmienia. Wygodnie wkleić podsumowanie B do A jedną wiadomością."
  - text: "Sesja A poprawia kod według uwag i ponownie uruchamia testy"
    why: "Pętla zamyka się sprawdzeniem: testy pokazują, że poprawki nie zepsuły reszty."
hint: "Kto pisze, kto sprawdza, jak wracają uwagi i czym wszystko się kończy?"
:::

::: step explain
Ważny niuans: recenzent poproszony o „znalezienie problemów” prawie zawsze coś znajdzie, nawet w dobrym kodzie. Jeśli gonić za każdą uwagą, kod obrośnie zbędnymi warstwami i sprawdzeniami.

Dlatego w prompcie recenzenta określa się, *co* sprawdzać i według jakiego planu, i prosi o zgłaszanie tylko tego, co wpływa na poprawność i wymagania.
:::

::: exercise write_prompt

  - "W jakiej formie zwrócić podsumowanie?"
  - "Czego recenzentowi nie wolno robić?"

review:
  task: "Uczeń na poziomie „Profesjonalista” pisze prompt dla osobnej sesji-recenzenta Claude Code (wzorzec „autor/recenzent”): recenzent ze świeżym kontekstem sprawdza kod napisany przez inną sesję. Lekcja uczy: określić, co sprawdzać i gdzie (gałąź, diff, pliki) (R1); dać punkt odniesienia — plan, specyfikację albo wymagania, oraz ważne przypadki brzegowe (R2); poprosić o zgłaszanie tylko usterek wpływających na poprawność i wymagania, a nie kwestii gustu, bo inaczej recenzent znajdzie rzeczy zbędne (R4); ustalić formę podsumowania, np. listę „plik — problem — dlaczego — jak poprawić”, i co napisać, jeśli problemów nie ma (R3); bonus — granice: tylko review, bez samodzielnego poprawiania kodu (R9). Szczegóły funkcji uczeń może wymyślić."
  criteria: ["R1", "R2", "R3", "R4", "R9"]
  reference_prompt: |

    - odpowiedź jest taka sama dla zarejestrowanego i niezarejestrowanego adresu e-mail, żeby nie dało się sprawdzić, kto ma konto;

    - "Czy wymieniono ważne przypadki brzegowe?"

::: step summary
**Równolegle znaczy w izolacji.**

- `claude --worktree <nazwa>`: własny folder i gałąź dla każdej sesji.
- `claude agents`: sesje w tle na jednym ekranie, każda we własnym worktree.
- Limity zużywa każda sesja osobno.
- „Autor/recenzent”: świeży kontekst sprawdza uczciwiej; proś tylko o istotne uwagi.

Moduł ukończony: teraz Claude pracuje dla ciebie i według harmonogramu, i równolegle.
:::
