::: step hook
Liam's `claude -p` script works, but only while his laptop is on. On Friday evening he shut the lid and headed off to the coast for the weekend. On Saturday morning, there was no report.

He needs a "colleague" who works on their own, without his computer.
:::

::: step explain
That's a *routine*: a saved Claude Code task (a prompt, repositories and connectors) that runs by itself in the cloud. Your laptop can be switched off.

Routines are available on the {{data.plans.pthree_routines_plans}} plans. Status: {{data.plans.pthree_routines_status}}.

You can create a routine at {{data.ui_paths.pthree_routines_page}} with the {{data.ui_paths.pthree_new_routine}} button, in the Desktop app or with the `/schedule` command in the CLI.
:::

::: step explain
A routine starts on a *trigger*. There are three kinds, and you can combine them:

- {{data.ui_paths.pthree_trigger_schedule}}: hourly, daily, on weekdays, weekly or once at a set time. The minimum interval is {{data.limits.pthree_cloud_min_interval}};
- {{data.ui_paths.pthree_trigger_api}}: an HTTP POST request to the routine's URL with a token;
- {{data.ui_paths.pthree_trigger_github}}: a new pull request or release in the repository.
:::

  - left: "Check every new pull request against the team's checklist"
    right: "GitHub event: pull_request.opened"
    why: "The routine reacts to an event in the repository. For that, the Claude GitHub App has to be installed on the repository."
  - left: "In two weeks' time, open a PR that removes a temporary flag"
    right: "Schedule, one-off run"
    why: "A one-off schedule fires once at the set time, and then the routine switches itself off."
hint: "Ask yourself: is the task started by the calendar, an external system or an event in the repository?"
:::

::: step explain
The most important part of a routine is the prompt. A routine works on its own and *doesn't ask for permission* while it runs. There's nobody to ask.

So the prompt has to be *self-contained*: from the prompt alone, Claude understands what to do, where, in what order and what success looks like. It's the "colleague test" taken to the extreme: your colleague got a note and went off to work the night shift.
:::

::: exercise single_choice
id: "p3.2.e2"
type: "single_choice"
question: "Why should a routine prompt be more detailed than an ordinary message in a session?"
options:
  - text: "A routine works on its own and doesn't stop to ask questions, so everything it needs has to be in the prompt up front"
    correct: true
    why: "Yes. In a session you can correct Claude as you go. In a routine every run happens without you, and Claude will fill any gaps in the prompt with guesses."
  - text: "Routines use a weaker model, so it needs more words"
    correct: false
    why: "You pick the routine's model yourself in the form. It's not about the model; it's that there's nobody around."
  - text: "A routine remembers previous runs, and the prompt has to take that into account"
    correct: false
    why: "It's the opposite: every run is a new session with a fresh copy of the repository. Everything it needs comes from the prompt and the data each time."
  - text: "A long prompt is cheaper to process"
    correct: false
    why: "Prompt length doesn't make a run cheaper. What matters isn't length but completeness: goal, data, steps and a success criterion."
hint: "Imagine the task runs at night while you're asleep."
:::

::: step explain
There's one important detail about the API trigger. The URL and token appear only after you've saved the routine: open it for editing, add the {{data.ui_paths.pthree_trigger_api}} trigger and click {{data.ui_paths.pthree_generate_token}}. The token is shown only once, so save it to your secrets store straight away.

```bash
curl -X POST "$ROUTINE_URL" \
  -H "Authorization: Bearer $ROUTINE_TOKEN" \
  -H "anthropic-beta: experimental-cc-routine-2026-04-01" \
  -H "anthropic-version: 2023-06-01" \
  -H "Content-Type: application/json" \
  -d '{"text": "Alert: 500 errors on /checkout"}'
```
:::

question: "What's true about a routine's API trigger? Select all that apply."
options:
  - text: "The token is shown once, and you can't view it again later"
    correct: true
    why: "Yes. If you lose the token, you issue a new one with the Regenerate button."
  - text: "The text from the `text` field arrives in a `routine-fire-payload` block as untrusted data"
    correct: true
    why: "Yes. Claude won't follow instructions in that text unless the routine's own prompt says how to handle it. This protects you in case the token leaks."
  - text: "For the routine to analyse the alert, the prompt has to refer to the `routine-fire-payload` block explicitly"
    correct: true
    why: "Yes. For example: \"Analyse the alert in the routine-fire-payload block.\" Without a line like that, the text stays as background information."
  - text: "The `text` field is parsed as JSON, and the routine gets separate fields"
    correct: false
    why: "No. The value is free text. If you send JSON, the routine gets it as a single string."
  - text: "You can create an API trigger token with the `/schedule` command in the CLI"
    correct: false
    why: "No. The CLI can't create, change or delete tokens yet. API triggers are added on the web."
hint: "Remember: what's visible only once, how the request text is labelled, and where the API trigger is set up."
:::

::: exercise find_error

question: "Sophie in Ghent is writing a prompt for an overnight routine in an online shop's repository. Tap the weak spots."
prompt: "Check the dependencies and do the usual. Open a PR updating the packages that have new patch versions, and run the tests. If anything's unclear, ask me."
segments:
  - text: "Check the dependencies and do the usual. "
    weak: true
    why: "Claude doesn't know what \"the usual\" is: every run starts from scratch. Spell out exactly what to check, for example \"read package.json\"."
  - text: "Open a PR updating the packages that have new patch versions, "
    weak: false
    why: "Good: a clear result and a clear boundary — patch versions only, no risky major upgrades."
  - text: "and run the tests. "
    weak: false
    why: "Good: there's a way to check the work. You could make it stronger: \"if the tests fail, don't open the PR; describe the error instead\"."
  - text: "If anything's unclear, ask me."
    weak: true
    why: "A routine doesn't stop for questions: there's nobody to ask at night. Better to say up front what to do in a borderline case: \"skip the package and describe it in the report\"."
hint: "Read the prompt as if you were seeing the project for the first time and couldn't message anyone."
:::

::: step explain
Each run creates a new session: you can see what Claude did, open the changes and continue the conversation. The {{data.ui_paths.pthree_run_now}} button runs the routine immediately, which is handy for a first test.

Be careful with a green status. It only means "the session started and finished without an infrastructure failure". Whether the task actually got done, you can only see in the session itself.
:::

::: step explain
Now it's your turn. A good routine prompt answers five questions:

1. What needs doing, and why?
2. Where does the data come from: which files, PRs, time period?
3. In what order should things happen?
4. What does the result look like, and where should it go?
5. What should happen if something goes wrong?
:::

The task: go through yesterday's pull requests in the team's repository and prepare a digest. The lesson teaches a self-contained prompt: the goal and why (R1, R2), where to get the data and for what period (R2), steps in order (R5), the form and location of the result (R3), a success criterion and behaviour in borderline cases without asking a human, e.g. \"if there were no PRs, say so\" (R4), and boundaries on actions: what may and may not be changed, e.g. \"don't merge or push anything\" (R9).     You're preparing the morning digest for the backend team of a delivery service. The digest exists so that at the 10:00 stand-up we can see in 5 minutes which PRs are waiting for review and where the risks are.

    Data: pull requests in this repository that were opened or updated in the last 24 hours and target the main branch. Use the gh CLI.

    Steps:
    1. Make a list of those PRs.
    2. For each one, note: author, size of the change, whether it has tests, whether CI passed, how long it's been waiting for review.
    3. Flag risk: PRs with no tests, with failing CI or with changes in the migrations/ folder.

    If there were no PRs in the last 24 hours, create the file with a single line: "No new PRs". If you couldn't get the data for a PR, say so in the table; don't guess.

::: step summary
**A routine is a Claude Code task that runs by itself in the cloud.**

- Triggers: schedule, API, GitHub event; you can combine them.
- It doesn't ask for permission while running, so the prompt has to be self-contained.
- Text from the API arrives as untrusted data.
- Green status ≠ task done: read the session.
