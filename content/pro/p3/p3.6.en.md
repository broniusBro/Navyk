::: step hook
In one terminal, Dan in Utrecht asked Claude to build a new login form; in another, to fix a bug in the shopping basket. Ten minutes later, both sessions were editing the same `package.json`, and the tests were failing because of each other's changes.

Two sessions: a good idea. One folder shared between them: a bad one.
:::

::: step explain
The fix is a *git worktree*: a separate working folder with its own files and its own branch, but sharing the repository's history. Think of two workbenches in the same workshop: the tools are shared, but the pieces you're working on don't get in each other's way.

```bash
claude --worktree feature-auth
```

Claude creates the folder `.claude/worktrees/feature-auth/` on a new branch, `worktree-feature-auth`. For a second session, run the same command with a different name in another terminal.
:::

    correct: false

::: step explain
Three practical details:

- add `.claude/worktrees/` to `.gitignore` so the folders don't clutter your main checkout;
- a worktree is a fresh copy, so dependencies are installed again, and files like `.env` are copied over by `.worktreeinclude`;
- on exit, an empty unnamed worktree is removed automatically. If it has changes, Claude asks whether to keep it or remove it.
:::

::: step explain
When you have lots of sessions, it's handy to keep them on one screen. That's *agent view*, status: {{data.plans.pthree_agent_view_status}}.

```bash
claude agents
claude --bg "find out why the SettingsChangeDetector test is failing"
```

Each prompt starts a background session. Before editing files, it moves into its own worktree. Statuses such as Working, Needs input and Completed show at a glance who's waiting for you.
:::

::: step explain
Parallel work isn't just about speed. A session that has just written some code tends to think it's good. A fresh context looks at it more honestly.

That's the *writer/reviewer* pattern: session A writes, session B reviews without A's history, and A fixes things based on the feedback. A similar variant: one Claude writes the tests, another writes code that passes them.
:::

::: exercise order_steps
id: "p3.6.e4"
type: "order_steps"
question: "Put the steps of the writer/reviewer pattern in order."
shuffle: true
items:
  - text: "Session A implements API rate limiting"
    why: "The writer does the task as usual, in its own worktree."
  - text: "Session B, with a fresh context, checks A's code against the criteria: edge cases, race conditions, consistency with the project's style"
    why: "The reviewer doesn't see the writer's reasoning and judges only the result. That's why it spots things the writer took for granted."
  - text: "B's feedback is passed to session A"
    why: "A review that isn't passed on changes nothing. It's easiest to paste B's summary into A as a single message."
  - text: "Session A fixes the code based on the feedback and runs the tests again"
    why: "The loop closes with a check: the tests show the fixes haven't broken anything else."
hint: "Who writes, who checks, how does the feedback get back, and how does it all end?"
:::

::: step explain
An important subtlety: a reviewer asked to "find problems" will almost always find something, even in good code. If you chase every comment, the code ends up buried in unnecessary layers and checks.

So the reviewer's prompt says *what* to check and against which plan, and asks it to flag only what affects correctness and requirements.
:::

::: step summary
**Parallel means isolated.**

- `claude --worktree <name>`: a separate folder and branch for each session.
- `claude agents`: background sessions on one screen, each in its own worktree.
- Every session uses its own share of your limits.
- Writer/reviewer: a fresh context checks more honestly; ask only for issues that matter.

Module complete: Claude now works for you both on a schedule and in parallel.
:::
