::: step hook
Skrypt z `claude -p` działa Pawłowi, ale tylko dopóki laptop jest włączony. W piątek wieczorem zamknął klapę i pojechał na działkę. W sobotę rano raportu nie było.

Potrzebny jest „pracownik”, który działa sam, bez jego komputera.
:::

::: step explain
To jest *routine*: zapisane zadanie Claude Code — prompt, repozytoria i konektory — które samo uruchamia się w chmurze. Laptop może być wyłączony.

Routines są dostępne w planach {{data.plans.pthree_routines_plans}}. Status: {{data.plans.pthree_routines_status}}.

Routine utworzysz na stronie {{data.ui_paths.pthree_routines_page}} przyciskiem {{data.ui_paths.pthree_new_routine}}, w aplikacji Desktop albo poleceniem `/schedule` w CLI.
:::

::: step explain
Routine startuje, gdy zadziała *wyzwalacz* (trigger). Są trzy rodzaje wyzwalaczy i można je łączyć:

- {{data.ui_paths.pthree_trigger_schedule}}: co godzinę, codziennie, w dni robocze, co tydzień albo raz o wybranej porze. Minimalny interwał to {{data.limits.pthree_cloud_min_interval}};
- {{data.ui_paths.pthree_trigger_api}}: żądanie HTTP POST na adres routine z tokenem;
- {{data.ui_paths.pthree_trigger_github}}: nowy pull request albo release w repozytorium.
:::

::: step explain
W routine najważniejszy jest prompt. Routine działa sama i *nie pyta o zgodę* w trakcie pracy. Nie ma kogo dopytać.

Dlatego prompt musi być *samowystarczalny*: po przeczytaniu samego promptu Claude rozumie, co zrobić, gdzie, w jakiej kolejności i jak wygląda sukces. To „test kolegi” w wersji ekstremalnej: kolega dostał karteczkę i poszedł na nocną zmianę.
:::

::: step explain
Wyzwalacz API ma ważny szczegół. Adres i token pojawią się po zapisaniu routine: otwórz ją do edycji, dodaj wyzwalacz {{data.ui_paths.pthree_trigger_api}} i kliknij {{data.ui_paths.pthree_generate_token}}. Token jest pokazywany tylko raz — od razu zapisz go w menedżerze sekretów.

```bash
curl -X POST "$ROUTINE_URL" \
  -H "Authorization: Bearer $ROUTINE_TOKEN" \
  -H "anthropic-beta: experimental-cc-routine-2026-04-01" \
  -H "anthropic-version: 2023-06-01" \
  -H "Content-Type: application/json" \
  -d '{"text": "Alert: błędy 500 na /checkout"}'
```
:::

  - text: "Sprawdź zależności i zrób to co zwykle. "
    weak: true
    why: "Claude nie wie, co znaczy „to co zwykle”: każde uruchomienie zaczyna się od zera. Opisz, co dokładnie sprawdzić, np. „przeczytaj package.json”."
  - text: "Otwórz PR z aktualizacją pakietów, które mają nowe wersje patch, "
    weak: false
    why: "Dobrze: jasny wynik i wyraźna granica — tylko wersje patch, bez ryzykownych dużych aktualizacji."
  - text: "i uruchom testy. "
    weak: false
    why: "Dobrze: jest sposób sprawdzenia. Można to wzmocnić: „jeśli testy nie przechodzą, nie otwieraj PR, tylko opisz błąd”."
  - text: "Jeśli coś jest niejasne, zapytaj mnie."
    weak: true
    why: "Routine nie zatrzymuje się na pytania: w nocy nie ma kogo zapytać. Lepiej z góry napisać, co zrobić w wątpliwym przypadku: „pomiń pakiet i opisz go w raporcie”."
hint: "Przeczytaj prompt tak, jakbyś widział projekt pierwszy raz i nie mógł do nikogo napisać."
:::

::: step explain
Każde uruchomienie tworzy nową sesję: widzisz, co zrobił Claude, możesz otworzyć zmiany i kontynuować rozmowę. Przycisk {{data.ui_paths.pthree_run_now}} uruchamia routine od razu — wygodne przy pierwszym teście.

Uważaj na zielony status. Oznacza tylko „sesja wystartowała i zakończyła się bez awarii infrastruktury”. Czy zadanie zostało wykonane, widać dopiero w samej sesji.
:::

  - text: "Usunąć routine i utworzyć ją od nowa"
    correct: false
    why: "Najpierw ustal przyczynę. Nowa routine z tym samym promptem najpewniej powtórzy ten sam problem."
  - text: "Zmienić harmonogram na co godzinę, żeby częściej próbować"
    correct: false
    why: "Częstotliwość nie usunie przyczyny, za to szybciej zużyje limity subskrypcji."
hint: "Gdzie widać nie „uruchomienie się odbyło”, tylko „co zrobił Claude”?"
:::

::: step explain
Teraz ty. Dobry prompt dla routine odpowiada na pięć pytań:

1. Co zrobić i po co?
2. Skąd brać dane: jakie pliki, PR, okres?
3. W jakiej kolejności działać?
4. Jak wygląda wynik i gdzie go zapisać?
5. Co robić, jeśli coś pójdzie nie tak?
:::

::: exercise write_prompt
id: "p3.2.e6"
type: "write_prompt"
question: "Napisz samowystarczalny prompt dla routine, która w każdy dzień roboczy rano przegląda wczorajsze pull requesty w repozytorium twojego zespołu i przygotowuje podsumowanie. Projekt i szczegóły możesz wymyślić. Nie wklejaj tokenów, haseł ani cudzych danych osobowych."

  - "Po co zespołowi to podsumowanie?"
  - "Co sprawdzić w każdym PR?"
  - "Jak wygląda wynik i gdzie go zapisać?"
  - "Co zrobić, jeśli PR nie było albo brakuje danych?"
  - "Czego routine nie powinna robić?"
min_chars: 120
hint: "Pisz dla kolegi, który idzie na nocną zmianę i nie będzie mógł do ciebie zadzwonić: cel, dane, kroki, wygląd wyniku, co robić w wątpliwych przypadkach i czego nie ruszać."
review:
  task: "Uczeń na poziomie „Profesjonalista” pisze prompt dla routine Claude Code — zadania w chmurze, które uruchamia się według harmonogramu (w każdy dzień roboczy rano) bez człowieka i w trakcie działania nie pyta o zgodę. Zadanie: przejrzeć wczorajsze pull requesty w repozytorium zespołu i przygotować podsumowanie. Lekcja uczy samowystarczalnego promptu: cel i po co (R1, R2), skąd brać dane i z jakiego okresu (R2), kroki po kolei (R5), forma i miejsce wyniku (R3), kryterium sukcesu i zachowanie w wątpliwych przypadkach bez pytania człowieka, np. „jeśli PR nie było — napisz to” (R4), granice działań: co wolno zmieniać, a czego nie, np. „niczego nie merguj i nie pushuj” (R9). Zwroty „zapytaj mnie”, „to co zwykle”, „sam się zorientujesz” to luka: routine nie może zapytać i nie pamięta poprzednich uruchomień. Szczegóły projektu uczeń może wymyślić."
  criteria: ["R1", "R2", "R3", "R4", "R5", "R9"]
  reference_prompt: |
    Przygotowujesz poranne podsumowanie dla zespołu backendu serwisu dostaw. Podsumowanie jest potrzebne, żeby na daily o 10:00 w 5 minut zobaczyć, które PR czekają na review i gdzie są ryzyka.

    Dane: pull requesty w tym repozytorium, które zostały otwarte lub zaktualizowane w ciągu ostatnich 24 godzin i są skierowane do gałęzi main. Użyj gh CLI.

    Kroki:
    1. Zrób listę takich PR.
    2. Dla każdego ustal: autora, rozmiar zmian, czy ma testy, czy przeszło CI, jak długo czeka na review.
    3. Oznacz ryzyko: PR bez testów, z nieprzechodzącym CI albo ze zmianami w folderze migrations/.

  show_reference: true
  fallback_feedback:

::: step summary
**Routine to zadanie Claude Code, które samo uruchamia się w chmurze.**

- Wyzwalacze: harmonogram, API, zdarzenie GitHub; można je łączyć.
- W trakcie działania nie pyta o zgodę — prompt musi być samowystarczalny.
- Tekst z API trafia jako niezaufane dane.
- Zielony status ≠ zadanie wykonane: czytaj sesję.

Dalej: kiedy routine, a kiedy zadanie na własnym komputerze albo `/loop`.
:::
