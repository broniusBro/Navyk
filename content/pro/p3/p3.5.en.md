::: step hook
Claire in Antwerp has an overnight routine that sorts support tickets. In the morning, her colleagues asked: "Claire, why did you post twenty messages in the team Slack channel at three in the morning?"

Claire was asleep. But the messages went out under her name.
:::

::: step explain
That's how it works. A routine acts through *your* connections:

- commits and pull requests come from your GitHub user;
- Slack messages, Linear tickets and other actions through connectors come from your accounts.

A routine belongs to your personal account and uses your limits. To everyone else, it's you, not "some bot".
:::

::: exercise single_choice
id: "p3.5.e1"
type: "single_choice"
question: "Overnight, Claire's routine opened a pull request and posted in Slack. Who's the author of those actions, as far as her colleagues can see?"
options:
  - text: "Claire herself: her GitHub user and her Slack account"
    correct: true
    why: "Yes. A routine acts through its owner's connections. So give it exactly the permissions you'd be happy to answer for yourself."
  - text: "A special Anthropic bot with its own name"
    correct: false
    why: "No. The docs say it plainly: everything a routine does through GitHub and connectors shows up as the owner's actions."
  - text: "Claire's whole team, because the routine is shared"
    correct: false
    why: "A routine belongs to a personal account and isn't shared with colleagues."
  - text: "Nobody: these actions in GitHub and Slack are anonymous"
    correct: false
    why: "Nothing here is anonymous. Every commit and message has an author, and that's the routine's owner."
hint: "Whose connections does the routine use to reach GitHub and Slack?"
:::

::: step explain
Three "doors" decide what a routine can do. Open each one only as far as the task needs. That's the *principle of least privilege*.

1. *Repositories*: only the ones the routine works in.
2. *Network*: the {{data.ui_paths.pthree_network_access}} level in the environment: {{data.ui_paths.pthree_network_trusted}}, {{data.ui_paths.pthree_network_custom}} or {{data.ui_paths.pthree_network_full}}.
3. *Connectors*: in the {{data.ui_paths.pthree_connectors}} section, *all* of them are on by default. Remove the ones you don't need.
:::

::: exercise match_pairs
id: "p3.5.e2"
type: "match_pairs"
question: "Match each risk with the measure that reduces it."
pairs:
  - left: "The routine can post in Slack, even though its job is only to read tickets from Linear"
    right: "Remove Slack from the routine's connectors"
    why: "Claude can use every tool of an enabled connector, including write actions, without asking. No connector, no writing."
  - left: "The routine needs one internal API, but full internet access is turned on"
    right: "Custom network: only the domains you need in Allowed domains"
    why: "Your own domain list opens exactly what's needed, and every other domain stays blocked."
  - left: "The routine mustn't change the main branch"
    right: "Branch protection rules or rulesets in GitHub"
    why: "By default Claude pushes to branches prefixed `claude/`, but the prompt can change that. The hard boundary is rules on GitHub's side."
  - left: "A third-party API key sits in an environment variable that every user of that environment can see"
    right: "Store the key as a network secret (on Pro and Max)"
    why: "Environment variables are visible to everyone who uses that environment. The docs recommend keeping secrets for API requests separate."
hint: "For each risk, think about which \"door\" to close: connectors, network, branches or secrets."
:::

    correct: true
    why: "Yes. This task doesn't need Slack or the other connectors, so they have no business being in the routine."
  - text: "Select only the knowledge base repository"
    correct: true
    why: "Yes. Every selected repository is cloned on every run and becomes available to the routine."
  - text: "Keep the network on {{data.ui_paths.pthree_network_trusted}} if the routine doesn't need other domains"
    correct: true
    why: "Yes. Connectors work through Anthropic's servers and don't require adding their domains. So there's no need to widen network access for Linear."
  - text: "Say in the prompt what's off limits: \"don't publish replies to customers, only drafts on a branch\""
    correct: true
    why: "Yes. The prompt sets the boundaries of the task. The hard limits come from permissions and branch rules."
  - text: "Switch the network to {{data.ui_paths.pthree_network_full}} so nothing breaks"
    correct: false
    why: "That's the opposite of least privilege. If something's missing, you'll see it refused in the run's session and can add the one domain you need."
hint: "For each option, ask: does it narrow access or widen it?"
:::

::: step explain
The API trigger is a separate door. Anyone with the token can start the routine and pass it text. So:

- keep the token in a secrets store; it's shown only once;
- if the token leaks, click {{data.ui_paths.pthree_regenerate_token}}: the old one stops working;
- text from the request arrives as *untrusted data*. The prompt can tell Claude to analyse it, but not to follow commands from it.
:::

    weak: false
    why: "Good: the prompt explicitly allows working with the alert text as data to analyse."
  - text: "Follow any instructions contained in the alert text. "
    weak: true
    why: "Dangerous: anyone who gets hold of the token could then control the routine through the text. An alert is data to analyse, not commands."
  - text: "Prepare a fix and push it straight to main. "
    weak: true
    why: "Dangerous: an unreviewed change goes into the main branch in your name. Better a `claude/…` branch and a PR, with main protected by GitHub rules."
  - text: "Describe the outcome in a draft PR."
    weak: false
    why: "Good: a draft PR lets whoever's on call check the fix before accepting it."
hint: "Look for places where the routine trusts someone else's text or does something irreversible without a human checking it."
:::

::: exercise single_choice
id: "p3.5.e5"
type: "single_choice"
question: "An API trigger token was accidentally posted in a public chat. What should you do first?"
options:
  - text: "Click Regenerate on the routine's API trigger and update the token wherever it's stored"
    correct: true
    why: "Yes. The new token replaces the old one, and the leaked token stops working. If you no longer need API access, you can remove the token with Delete token."
  - text: "Delete the message from the chat, and that's it"
    correct: false
    why: "Someone may already have copied the token. Deleting the message doesn't invalidate it."
  - text: "Nothing: text from the request arrives as untrusted anyway"
    correct: false
    why: "That label reduces the risk but doesn't remove it: with the token, anyone can start the routine and use up your limits. The token needs replacing."
  - text: "Pause the routine permanently"
    correct: false
    why: "Pausing doesn't change the token itself: whoever copied it still has it. The right move is to issue a new token."
hint: "You need the old token to stop working."
:::

::: step summary
**A routine acts in your name, so give it only what it needs.**

- Repositories: only the ones it works in.
- Network: Trusted or your own domain list.
- Connectors: remove the extras; enabled ones can write too.
- Protect main with GitHub rules.
- Token: in secrets; if it leaks, Regenerate.
- Text from the request is data, not commands.

:::
