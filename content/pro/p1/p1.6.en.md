::: step hook
Dave writes to Claude Code:

```prompt
add Google sign-in
```

Claude immediately changes nine files. Half an hour later it turns out the project already had its own session system, and the new sign-in broke it. Claude solved the wrong problem because it never took the time to understand the code.
:::

::: step explain
The docs recommend splitting a task into four phases:

1. **Explore.** Claude reads the code and answers questions without changing anything.
2. **Plan.** Claude writes a detailed plan.
3. **Code.** Claude writes the code to the plan and checks it with tests.
4. **Commit.** A commit with a clear description, and a pull request.
:::

  - text: "“Commit with a clear description and open a pull request”"
    why: "Commit: you lock in the result once everything's been checked."
hint: "First understand, then decide, then do, then save."
:::

::: step explain
Run the first two phases in *plan mode*: Claude reads files and explores the project but doesn't edit any code.

How to enter it:

- press {{data.ui_paths.p1_shift_tab}} until you see {{data.ui_paths.p1_status_plan}};
- or start your prompt with `/plan`;
- or launch the session like this:

```bash
claude --permission-mode plan
```
:::

::: step explain
When the plan is ready, Claude asks what to do next:

- {{data.ui_paths.p1_plan_yes_auto}};
- {{data.ui_paths.p1_plan_yes_manual}};
- {{data.ui_paths.p1_plan_keep}}.

Want to edit the plan yourself? Press {{data.ui_paths.p1_ctrl_g}}.
:::

::: step explain
A plan isn't always a good idea. It takes time.

The rule from the docs: **if you can describe the change in one sentence, skip the plan.** A typo, a new log line, a renamed variable — just ask for it.

A plan helps when you're unsure of the approach, the change touches several files or the code is new to you.
:::
