::: step hook
Дмитро пише Claude Code:

```prompt
додай вхід через Google
```

Claude одразу змінює дев'ять файлів. За пів години з'ясовується: у проєкті вже була своя система сесій, і новий вхід її зламав. Claude розв'язував не те завдання, бо не встиг розібратися.
:::

::: step explain
Документація радить ділити завдання на чотири фази:

1. **Explore — вивчити.** Claude читає код і відповідає на запитання, нічого не змінюючи.
2. **Plan — спланувати.** Claude пише докладний план.
3. **Code — зробити.** Claude пише код за планом і перевіряє його тестами.
4. **Commit — зафіксувати.** Коміт зі зрозумілим описом і запит на злиття.
:::

::: step explain
Перші дві фази проводь у *режимі планування* (plan mode): Claude читає файли й вивчає проєкт, але не редагує код.

Як увійти:

- натискай {{data.ui_paths.p1_shift_tab}}, доки не з'явиться напис {{data.ui_paths.p1_status_plan}};
- або почни запит із `/plan`;
- або запусти сесію так:

```bash
claude --permission-mode plan
```
:::

::: step explain
Коли план готовий, Claude спитає, що далі:

- {{data.ui_paths.p1_plan_yes_auto}};
- {{data.ui_paths.p1_plan_yes_manual}};
- {{data.ui_paths.p1_plan_keep}}.

Хочеш поправити план сам? Натисни {{data.ui_paths.p1_ctrl_g}}.
:::

::: step explain
План — не завжди добра ідея. Він забирає час.

Правило з документації: **якщо зміну можна описати одним реченням, план не потрібен.** Друкарська помилка, новий рядок у лозі, перейменування змінної — просто попроси зробити.

План корисний, коли ти не впевнений у підході, правка зачіпає кілька файлів або код тобі незнайомий.
:::

::: step summary
