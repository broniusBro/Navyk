::: step hook
Дмитрий пишет Claude Code:

```prompt
добавь вход через Google
```

Claude сразу меняет девять файлов. Через полчаса выясняется: в проекте уже была своя система сессий, и новый вход её сломал. Claude решал не ту задачу, потому что не успел разобраться.
:::

::: step explain
Документация советует разделять задачу на четыре фазы:

1. **Explore — изучить.** Claude читает код и отвечает на вопросы, ничего не меняя.
2. **Plan — спланировать.** Claude пишет подробный план.
3. **Code — сделать.** Claude пишет код по плану и проверяет его тестами.
4. **Commit — зафиксировать.** Коммит с понятным описанием и запрос на слияние.
:::

::: step explain
Первые две фазы проводи в *режиме планирования* (plan mode): Claude читает файлы и изучает проект, но не правит код.

Как войти:

- нажимай {{data.ui_paths.p1_shift_tab}} до надписи {{data.ui_paths.p1_status_plan}};
- или начни запрос с `/plan`;
- или запусти сессию так:

```bash
claude --permission-mode plan
```
:::

::: step explain
Когда план готов, Claude спросит, что дальше:

- {{data.ui_paths.p1_plan_yes_auto}};
- {{data.ui_paths.p1_plan_yes_manual}};
- {{data.ui_paths.p1_plan_keep}}.

Хочешь поправить план сам? Нажми {{data.ui_paths.p1_ctrl_g}}.
:::

::: step explain
План — не всегда хорошая идея. Он занимает время.

Правило из документации: **если изменение можно описать одним предложением, план не нужен.** Опечатка, новая строка в логе, переименование переменной — просто попроси сделать.

План полезен, когда ты не уверен в подходе, правка затрагивает несколько файлов или код тебе незнаком.
:::
