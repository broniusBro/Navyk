::: step hook
Claude Code writes:

```claude
Done! The email validation function has been added and works.
```

You open the site, type `anna@.com`, and the form accepts it. “Works” turned out to be just a word.

Why? Claude stops when the work *looks* finished. If it has no way to check itself, the checking falls to you.
:::

::: step explain
Give Claude a *way to verify*: something that answers “pass” or “fail”:

- tests;
- a project build: did it build or fail with an error;
- a linter, a program that looks for problems in code;
- a script that compares the result with a reference;
- a screenshot of the page next to the design mock-up.

Then the loop closes without you: do → check → fix → check again.
:::

  - text: "The second prompt has examples and a command to check with, so Claude found and fixed the bug itself"
    correct: true
    why: "Exactly. The user@.com test failed, Claude saw it and fixed it. In the first case, only you would have found that bug, and only once it was on the site."
  - text: "The second time, Claude just tried harder"
    correct: false
    why: "Claude doesn't “try harder”. The difference is that it now had a way to find out about its mistake."
  - text: "The first answer is better: it's shorter and to the point"
    correct: false
    why: "Shorter, but unchecked. “Done!” proves nothing, and the user@.com bug is still there."
  - text: "The only difference is that the second prompt names the function"
    correct: false
    why: "The function name is a detail. What matters is the examples with expected results and the request to run the tests."
hint: "Find the moment in the second answer where Claude learned about its mistake. What did that let it do?"
:::

::: step explain
Three techniques from the docs:

1. **Give criteria.** Example inputs with expected outputs, plus a request to run the tests.
2. **Check the UI visually.** Attach a screenshot of the design and ask Claude to screenshot the result, compare the two and fix the differences.
3. **Fix the cause, not the symptom.** “Fix the build error and make sure the build passes. Don't switch off the check.”
:::

::: exercise match_pairs
id: "p1.7.e2"

question: "Match each task with the way of verifying it that fits best."
pairs:
  - left: "A function that calculates a discount"
    right: "Tests with examples: input amount and expected discount"
    why: "For a function with a clear input and output, tests are the most direct pass/fail signal."
  - left: "A new page should look like the designer's mock-up"
    right: "A screenshot of the result next to the mock-up"
    why: "You can't describe appearance with a test. A screenshot lets Claude see the differences and fix them."
  - left: "The project stopped building after a library update"
    right: "The build passes with no errors"
    why: "A build's exit code is a clear signal. And crucially: it passes because the cause was fixed, not because the check was switched off."
  - left: "A script that produces a monthly report"
    right: "Comparing the output with a known-good reference report"
    why: "If there's a correct reference, the script's output can be compared with it to show any differences."
hint: "Ask yourself: how would you know the task was done?"
:::

::: exercise find_error
id: "p1.7.e3"
type: "find_error"
question: "Tom is giving Claude Code a task. Tap the parts where Claude won't be able to check itself, or where the check will be fake."
prompt: "Make the checkout page prettier. Fix the build error — if it gets in the way, just turn off type checking. Fix the delivery calculation: delivery is free on orders over €50, write a test for it and run it. Tell me when you're done."
segments:
  - text: "Make the checkout page prettier. "
    weak: true
    why: "“Prettier” can't be checked. Better to attach a mock-up or screenshot and ask Claude to compare the result against it."
  - text: "Fix the build error — if it gets in the way, just turn off type checking. "
    weak: true
    why: "That's treating the symptom: the build will pass, but the error will still be there. Better: “find the cause and fix it; don't switch off any checks”."
  - text: "Fix the delivery calculation: delivery is free on orders over €50, write a test for it and run it. "
    weak: false
    why: "A great part: there's a rule, a test and an instruction to run it. Claude will find out for itself whether it worked."
  - text: "Tell me when you're done."
    weak: true
    why: "“Done” isn't evidence. Better to ask to see the test and build output."
hint: "Look for three things: an uncheckable wish, a suppressed error and a request to take Claude's word for it."
:::

::: step explain
Don't ask Claude to “tell you it works”; ask for *evidence*: the test output, which command it ran and what came back, a screenshot of the result.

Reading evidence is quicker than rechecking everything yourself. And it works even if you stepped away while Claude was working.

The rule from the docs: **if you can't verify it, don't ship it.**
:::

::: exercise single_choice
id: "p1.7.e4"
type: "single_choice"
question: "Claude has finished and says: “Everything's fixed, the tests pass.” What's the best reply?"
options:
  - text: "“Show me the command you used to run the tests, and its output”"
    correct: true
    why: "Correct. That way you see evidence, not a claim. If there are fewer tests than you expected, or one was skipped, you'll spot it straight away."
  - text: "“Great, thanks!” — and ship the changes"
    correct: false
    why: "You took it on trust. If Claude ran the wrong tests or not all of them, the bug will reach your users."
  - text: "“Check again, very carefully”"
    correct: false
    why: "A request without a way to check adds nothing. You need a concrete result, not a promise."
  - text: "Recheck everything by hand yourself, line by line, straight away"
    correct: false
    why: "You could, but it's slow. Look at the test output first, which is quicker, then check by hand whatever the tests don't cover."
hint: "What's quicker and more reliable: taking it on trust, rechecking everything yourself or looking at the evidence?"
:::

::: step summary
**Claude stops when the work looks done. Give it a way to check that it really is.**

Tests, a build, a screenshot next to the mock-up — and a request to show the output. If you can't verify it, don't ship it.
