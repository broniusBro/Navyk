::: step hook
Олег із Дніпра запустив бота підтримки для інтернет-провайдера. Клієнт пише: «Знову немає інтернету!!!» Бот відповідає:

```claude
Інтернет — це глобальна система об'єднаних комп'ютерних мереж. Причини відсутності підключення можуть бути різноманітними: від несправності обладнання до…
```

Технічно правильно, по суті марно. Бот не знає, хто він і навіщо тут.
:::

::: step explain
В API у запиту є окреме поле `system` — *системний промпт*. Це постійна пам'ятка для Claude на всю розмову: ким бути і як працювати.

У `messages` іде сам діалог: що пише користувач. Це як інструкції проєкту в чаті, тільки їх задає твій код.
:::

::: step explain
```python
message = client.messages.create(
    model="{{data.models.pfour_sonnet_id}}",
    max_tokens=1024,
    system="Ти оператор підтримки інтернет-провайдера «Мережа-Дніпро»…",
    messages=[{"role": "user", "content": "Знову немає інтернету!!!"}],
)
```

Навіть одне речення про роль змінює тон і фокус відповіді.
:::

  - text: "«Знову немає інтернету!!!» — текст клієнта"
    correct: false
    why: "Це репліка конкретного користувача. Вона йде в messages з роллю user."
  - text: "Ключ API, щоб Claude знав, хто його викликає"
    correct: false
    why: "Ключ передається в заголовку x-api-key і ніколи не потрапляє в текст промпту. Claude він не потрібен."
hint: "system — правила на всю розмову, messages — те, що відбувається в розмові."
:::

::: step explain
Сильний системний промпт складається з тих самих частин, що й інструкції проєкту:

- *роль*: ким бути;
- *контекст і навіщо*: що за продукт і чому правила саме такі;
- *правила*: що робити в типових і складних випадках;
- *формат*: довжина й вигляд відповіді.

Правила пиши як «що робити» і пояснюй причину: Claude узагальнює пояснення краще, ніж голу заборону.
:::

    role: "goal"

  - id: "b4"

    role: "format"

    text: "НІКОЛИ НЕ ПИШИ ДОВГО!!!"
    role: "noise"
    why: "Капслок і заборона без міри. Блок із форматом уже сказав, якої довжини відповідь, і зробив це спокійно й конкретно."
  - id: "b6"
    text: "Ключ API: sk-ant-api03-…"
    role: "noise"

hint: "Порядок як в інструкції проєкту: хто ти, що за ситуація і чому, що робити, як оформити відповідь."
:::

  - text: "Не використовуй markdown. "

  - text: "Не обговорюй ціни. "
    weak: true
    why: "Незрозуміло, що робити, коли запитають про ціну, і чому. Краще: «На запитання про ціни відповідай, що вартість назве лікар після огляду, і пропонуй записатися на консультацію»."
  - text: "Пропонуй час лише з розкладу в тегу <schedule>, бо запис без вільного вікна зірве прийом іншого пацієнта."
    weak: false
    why: "Чудово: є правило, джерело даних у тегу й причина. Claude зрозуміє, чому не можна вигадувати час."
hint: "Шукай правила на «не»: чи сказано, що робити натомість і навіщо?"
:::

::: step explain
Коли в системний промпт потрапляють дані (розклад, прайс, документи), відокремлюй їх *XML-тегами*: `<schedule>…</schedule>`, `<faq>…</faq>`.

Теги допомагають Claude не плутати інструкції з даними. Назви обирай зрозумілі й однакові в усьому промпті.
:::

::: step explain
Тепер сам. Придумай продукт, якому потрібен бот: служба доставки, онлайн-школа, барбершоп, застосунок для бігу.

Напиши системний промпт повністю. Navyk надішле його на розбір Claude. Справжніх ключів, телефонів та імен клієнтів не пиши.
:::

Урок навчає: роль (P7), контекст із причиною (P2), правила як «що робити» (P3), формат відповіді, дані в XML-тегах окремо від інструкцій. ::: step summary
**Системний промпт — постійна пам'ятка застосунку: роль, контекст із причиною, правила й формат.**

Дані — у XML-теги, правила — як «що робити», ключ — лише в заголовку запиту.

Далі: як керувати глибиною міркувань через effort.
:::
