::: step hook
For every piece of feedback, Navyk's reviewer sends Claude the same long instructions with a rubric. Only your prompt at the end changes.

Thousands of reviews a day, each paying full price for the same opening. Is there a way to stop re-reading it every time?
:::

::: step explain
There is: *prompt caching*. Claude saves the processed beginning of the request, the *prefix*, and reads it from the cache next time. It's cheaper and faster.

The prefix is built in the order `tools` → `system` → `messages`. So put what stays the same at the start and what changes at the end.
:::

::: step explain
Mark the point to cache up to with the `cache_control` field:

```python
response = client.messages.create(
    model=MODEL_ID,
    max_tokens=1500,
    system=[{
        "type": "text",
        "text": LONG_INSTRUCTIONS,  # the part that stays the same
        "cache_control": {"type": "ephemeral", "ttl": "1h"},
    }],
    messages=[{"role": "user", "content": student_prompt}],  # changes
)
```

That's exactly how Navyk does it. Without `ttl` the cache lives for {{data.limits.pfour_cache_ttl_default}}; with `"ttl": "1h"`, for {{data.limits.pfour_cache_ttl_long}}.
:::

::: exercise single_choice
id: "p4.7.e1"
type: "single_choice"
question: "Where should the request's date and time go so they don't break the cache?"
options:
  - text: "At the end, in the user message after the cached part"
    correct: true
    why: "The cache works by matching the start of the request. Put anything that changes after the cache breakpoint."
  - text: "In the first line of the system prompt, so Claude knows the time straight away"
    correct: false
    why: "The start of the request is different every second, so the cache will never match. You'll pay for cache writes over and over."
  - text: "In the tool description: tools come first anyway"
    correct: false
    why: "Changing the tool descriptions invalidates the whole cache, because tools sit at the very start of the prefix."
hint: "The cache is a match on the beginning. Where will the changing part do the least harm?"
:::

::: step explain
What it costs compared with regular input:

- cache write (lifetime: {{data.limits.pfour_cache_ttl_default}}): {{data.prices.pfour_cache_write_5m}};
- cache write (lifetime: {{data.limits.pfour_cache_ttl_long}}): {{data.prices.pfour_cache_write_1h}};
- cache read: {{data.prices.pfour_cache_read}}.

Every hit extends the cache's life for free.
:::

id: "p4.7.e2"

question: "At night, reviews come in roughly once every 15 minutes. Which cache lifetime should you choose?"
options:
  - text: "{{data.limits.pfour_cache_ttl_long}}: the cache will last until the next request, and every hit extends it"
    correct: true
    why: "With requests every 15 minutes, a short cache will expire in between and you'll keep paying for new writes. The long cache costs more to write, but you'll rarely need to write it."
  - text: "{{data.limits.pfour_cache_ttl_default}}: the write is cheaper, so it's cheaper overall"
    correct: false
    why: "The write is cheaper, but it'll happen on every request, and there won't be any reads at all. The cache simply won't get a chance to pay off."
  - text: "It doesn't matter: the cache lives for a day either way"
    correct: false
    why: "No, there are two options: {{data.limits.pfour_cache_ttl_default}} by default and {{data.limits.pfour_cache_ttl_long}} with ttl \"1h\"."
hint: "Compare the gap between requests with the cache lifetime."
:::

::: step explain
Two traps:

- *Minimum length.* A short prefix isn't cached, even with `cache_control`, and there's no error. The minimum: {{data.limits.pfour_cache_min_tokens}}.
- *Invalidation.* Change the tools and everything is invalidated. Change the system prompt and it's invalidated along with the messages.

A request can have up to {{data.limits.pfour_cache_breakpoints}} `cache_control` breakpoints.
:::

::: exercise find_error
id: "p4.7.e3"
type: "find_error"
question: "Dan turned on caching for the garage bot, but the bill didn't go down. Tap the reasons."
prompt: "The system prompt starts with the line “It's now 14:32:07”. Then come 300 tokens of rules with cache_control on them. Every day at 9:00 I update the tool descriptions. The customer's question goes at the end, in messages."
segments:
  - text: "The system prompt starts with the line “It's now 14:32:07”. "
    weak: true
    why: "The time at the start changes with every request, so the prefix will never match. Move the time to the end, into the user message."
  - text: "Then come 300 tokens of rules with cache_control on them. "
    weak: true
    why: "That's shorter than the minimum length for caching. A prefix like this silently isn't cached: cache_control is there, but there are no savings."
  - text: "Every day at 9:00 I update the tool descriptions. "
    weak: false
    why: "Invalidating the cache once a day is fine: after that it works all day again. Changing the tools on every request would be the problem."
  - text: "The customer's question goes at the end, in messages."
    weak: false
    why: "Correct: the changing part comes after the cached part."
hint: "Look for something at the start that changes with every request, and something too short to be cached."
:::

::: step explain
How do you check the cache is working? Look at `usage` in the response:

- `cache_creation_input_tokens`: how much was written to the cache;
- `cache_read_input_tokens`: how much was read from the cache;
- `input_tokens`: tokens after the last cache breakpoint.

If reads are always 0, the cache isn't kicking in.
:::

::: exercise match_pairs
id: "p4.7.e4"
type: "match_pairs"
question: "Match what you see in usage with what it tells you."
pairs:
  - left: "First request: cache_creation_input_tokens = 3000, cache_read_input_tokens = 0"
    right: "The cache was written; that's normal for the first request"
    why: "The first request always writes the cache, and a write costs more than regular input. The savings start with the next one."
  - left: "Second request a minute later: cache_read_input_tokens = 3000"
    right: "The cache worked; the prefix was read at a discount"
    why: "Exactly what it was all for: 3,000 tokens read at the cache read price."
  - left: "Every request: cache_creation_input_tokens = 3000, reads always 0"
    right: "The start of the request differs each time, or the cache expires in between"
    why: "Look for changing data at the start of the request and compare the gap between requests with the cache lifetime."
  - left: "Both fields are always 0, even though cache_control is set"
    right: "The prefix is shorter than the minimum length"
    why: "A prefix that's too short isn't cached, and the API doesn't report an error. Check the minimum for your model."
hint: "Writes with no reads: the cache doesn't match. No writes and no reads: there's nothing to cache."
:::

::: step summary
**What stays the same goes first, under cache_control; what changes goes at the end.**

Choose the lifetime to suit how often requests come in, remember the minimum length and check `cache_read_input_tokens` in `usage`.
