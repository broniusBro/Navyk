::: step hook
Oceniający w Navyk przy każdej ocenie wysyła Claude tę samą długą instrukcję z kryteriami. Zmienia się tylko twój prompt na końcu.

Tysiące ocen dziennie i za każdym razem pełna cena za ten sam początek. Czy da się go nie czytać od nowa?
:::

::: step explain
Da się: to *buforowanie promptu*. Claude zapisuje przetworzony początek zapytania, czyli *prefiks*, i następnym razem czyta go z cache. To taniej i szybciej.

Prefiks składa się w kolejności `tools` → `system` → `messages`. Czyli to, co stałe, daj na początek, a to, co się zmienia, na koniec.
:::

::: step explain
Zaznacz miejsce, do którego buforować, polem `cache_control`:

```python
response = client.messages.create(
    model=MODEL_ID,
    max_tokens=1500,
    system=[{
        "type": "text",
        "text": LONG_INSTRUCTIONS,  # stała część
        "cache_control": {"type": "ephemeral", "ttl": "1h"},
    }],
    messages=[{"role": "user", "content": student_prompt}],  # zmienia się
)
```

Tak właśnie jest zrobione w Navyk. Czas życia cache bez `ttl`: {{data.limits.pfour_cache_ttl_default}}, z `"ttl": "1h"`: {{data.limits.pfour_cache_ttl_long}}.
:::

type: "single_choice"
question: "Gdzie umieścić datę i godzinę zapytania, żeby nie psuć cache?"
options:
  - text: "Na końcu, w wiadomości użytkownika po zbuforowanej części"
    correct: true
    why: "Cache działa na zasadzie zgodności początku zapytania. Wszystko, co się zmienia, umieszczaj za punktem buforowania."
  - text: "W pierwszej linijce promptu systemowego: wtedy Claude od razu zna godzinę"
    correct: false
    why: "Co sekundę początek zapytania jest inny, więc cache ani razu się nie zgodzi. Będziesz płacić za zapis do cache w kółko."
  - text: "W opisie narzędzia: narzędzia i tak idą pierwsze"
    correct: false
    why: "Zmiana opisu narzędzi unieważnia cały cache — narzędzia są na samym początku prefiksu."
hint: "Cache to zgodność początku. Gdzie zmienna część najmniej zaszkodzi?"
:::

::: step explain
Ile to kosztuje w porównaniu ze zwykłym wejściem:

- zapis do cache (czas życia: {{data.limits.pfour_cache_ttl_default}}): {{data.prices.pfour_cache_write_5m}};
- zapis do cache (czas życia: {{data.limits.pfour_cache_ttl_long}}): {{data.prices.pfour_cache_write_1h}};
- odczyt z cache: {{data.prices.pfour_cache_read}}.

Każde trafienie bezpłatnie przedłuża życie cache.
:::

    why: "Krótki cache przy zapytaniach co 15 minut zdąży wygasnąć i będziesz płacić za nowy zapis. Długi cache jest droższy przy zapisie, ale zapis będzie rzadki."
  - text: "{{data.limits.pfour_cache_ttl_default}}: zapis jest tańszy, więc w sumie wyjdzie taniej"
    correct: false
    why: "Zapis jest tańszy, ale będzie się odbywał przy każdym zapytaniu, a odczytów nie będzie wcale. Cache po prostu nie zdąży się przydać."
  - text: "Bez znaczenia: cache i tak żyje dobę"
    correct: false
    why: "Nie, są dwie opcje: {{data.limits.pfour_cache_ttl_default}} domyślnie i {{data.limits.pfour_cache_ttl_long}} z ttl \"1h\"."
hint: "Porównaj odstęp między zapytaniami z czasem życia cache."
:::

::: step explain
Dwie pułapki:

- *Minimalna długość.* Krótki prefiks nie jest buforowany, nawet z `cache_control`, i nie będzie błędu. Minimum: {{data.limits.pfour_cache_min_tokens}}.
- *Unieważnienie.* Zmienisz narzędzia — unieważni się wszystko. Zmienisz prompt systemowy — unieważni się on i wiadomości.

W zapytaniu może być do {{data.limits.pfour_cache_breakpoints}} punktów `cache_control`.
:::

::: step explain
Jak sprawdzić, czy cache działa? Patrz na `usage` w odpowiedzi:

- `cache_creation_input_tokens` — ile zapisano do cache;
- `cache_read_input_tokens` — ile odczytano z cache;
- `input_tokens` — tokeny po ostatnim punkcie buforowania.

Jeśli odczyt zawsze wynosi 0, cache nie działa.
:::

    right: "Cache zadziałał, prefiks odczytano ze zniżką"
    why: "Dokładnie o to chodziło: 3000 tokenów odczytano po cenie odczytu z cache."
  - left: "Każde zapytanie: cache_creation_input_tokens = 3000, odczyt zawsze 0"
    right: "Początek zapytania za każdym razem jest inny albo cache zdąży wygasnąć"
    why: "Szukaj zmiennych danych na początku zapytania i porównaj odstęp między zapytaniami z czasem życia cache."
  - left: "Oba pola zawsze 0, choć cache_control jest ustawiony"
    right: "Prefiks jest krótszy niż minimalna długość"
    why: "Za krótki prefiks nie jest buforowany, a API nie zgłasza błędu. Sprawdź minimum dla swojego modelu."
hint: "Zapis bez odczytu — cache się nie zgadza. Ani zapisu, ani odczytu — nie ma czego buforować."
:::

::: step summary
**To, co stałe, na początek i pod cache_control, a to, co zmienne, na koniec.**

Dobieraj czas życia do częstotliwości zapytań, pamiętaj o minimalnej długości i sprawdzaj `cache_read_input_tokens` w `usage`.

Dalej: przetwarzanie wsadowe ze zniżką.
:::
