::: step hook
Every Friday, Ellen in Edinburgh types the same long prompt into Claude Code: “Take the commits since the last tag, group them, strip the hashes, write it for users…”

Twelve lines, and every time she forgets something. She'd rather type `/release-notes 2.4.0` and get finished text.
:::

::: step explain
That's what a *skill* is for: a folder with a `SKILL.md` file. Think of it as a how-to sheet for a colleague: open it and follow the steps.

Where it lives:

- `.claude/skills/<name>/SKILL.md` — a project skill. Commit it and the whole team has it.
- `~/.claude/skills/<name>/SKILL.md` — a personal skill, available in all your projects.

The folder name becomes the command: `/release-notes`.
:::

::: step example
The file `.claude/skills/release-notes/SKILL.md`:

```markdown
---
description: Writes release notes from the commits since the last git tag. Use when asked for release notes or a list of changes for a release.
argument-hint: "[version]"
---

Put together release notes for version $ARGUMENTS.

1. Look at the commits since the last tag: `git log $(git describe --tags --abbrev=0)..HEAD --oneline`.
2. Group them under “New”, “Fixes” and “Other”.
3. Write for users: no commit hashes or file names.
4. Move unclear commits to the end, marked “to clarify”.
```

Invocation: `/release-notes 2.4.0`. `$ARGUMENTS` is replaced with `2.4.0`.
:::

::: step explain
Claude can also load a skill on its own, without a command. At the start of a session it sees only each skill's *description* (`description`) and uses it to decide whether the skill fits the task. A vague description, and the skill won't fire, or will fire in the wrong place.

Two fields control invocation:

- `disable-model-invocation: true` — only you, via `/name`. For skills with side effects, such as deploying.
- `user-invocable: false` — only Claude; the skill doesn't appear in the `/` menu.
:::

  - left: "`$ARGUMENTS` in the skill text"
    right: "Gets replaced with whatever you typed after the command"
    why: "In `/release-notes 2.4.0`, that's `2.4.0`. One skill works for any version."
hint: "One field is for Claude, two are about who can invoke the skill, and one more technique is about the text after the command."
:::

::: step explain
Now write your own skill. Pick a task you keep repeating in Claude Code: a pull request description, a code review against your team's checklist, triaging failing tests.

You need frontmatter with a `description` and step-by-step instructions. Navyk will send your skill to Claude for feedback. Don't put secrets or tokens in the skill.
:::

type: "write_prompt"
question: "Write the contents of SKILL.md for a skill you'd invoke with a command: YAML frontmatter with a `description` and step-by-step instructions."

ideas:

  - "Whether you need `disable-model-invocation: true`"
  - "What gets passed via `$ARGUMENTS`"
  - "Steps in order"
  - "What the result should look like"
  - "What to do if data is missing"

hint: "Start with the description: what the skill does and when to use it, in the words you'd type in a prompt yourself. Then the steps and what the result looks like. If the skill changes or publishes something, think about manual invocation."
review:
  task: "A Professional-level learner is writing SKILL.md for a Claude Code skill: YAML frontmatter between --- and Markdown instructions. Assess it as instructions for Claude. R1: the description makes clear what the skill does and when to use it (specific trigger words, not “a useful helper”). R2: the instructions include the necessary context — where to get the data (git commands, files), who the result is for. R3: the shape of the result is described. R4: it's clear what counts as a good result and what to do when data is missing. R5: steps in order. Bonus, no mark-down if absent: $ARGUMENTS and argument-hint; disable-model-invocation: true for a skill with side effects (deploying, publishing, sending messages) — if a skill with side effects lacks this field, gently suggest it. Don't require a specific skill topic. If the text contains tokens, passwords or keys, R10 applies."
  criteria: ["R1", "R2", "R3", "R4", "R5"]
  reference_prompt: |
    ---
    description: Writes a pull request description from the changes on the current branch. Use when asked for a PR description, pull request text or a summary of the branch's changes.
    argument-hint: "[ticket number]"
    ---

    Prepare a pull request description for ticket $ARGUMENTS.

    1. Look at the branch's changes against main: `git diff main...HEAD` and `git log main..HEAD --oneline`.
    2. Write a “What changed” section: 3–5 bullet points in plain language, for a reviewer who hasn't seen the ticket.
    3. Write a “How to test” section: steps the reviewer can repeat locally.
    4. If there are changes to migrations, configuration or the public API, move them into a “Heads-up” section.
    5. If the code doesn't make clear why a change was made, don't invent a reason: add a question to an “Ask the author” section.

    Format: Markdown, sections with level-two headings, no commit hashes.
  show_reference: true
  fallback_feedback:
    - "Does the description make clear what the skill does and which prompts it's for?"
    - "Is the description free of empty words like “useful” or “helps with code”?"
    - "Does it say where to get the data: which commands, files, branches?"
    - "Are the steps in order?"
    - "Is the shape of the result described: sections, length, audience?"
    - "Does it say what to do if data is missing, instead of guessing?"
    - "If the skill publishes or changes something, does it have `disable-model-invocation: true`?"
    - "Is the text free of tokens, passwords and keys?"
:::

::: step summary
**A skill is a folder with `SKILL.md`: frontmatter with a description, plus instructions. A project skill lives in `.claude/skills/<name>/` and is invoked with `/name`.**

The description decides whether the skill fires on its own. Run skills with consequences by hand only: `disable-model-invocation: true`.
