::: step hook
A colleague messages Ben in the team chat: “Run `/plugin install turbo-dev@super-tools`, it's got everything: skills, hooks, MCP. I installed it, it's brilliant!”

One command and you get a ready-made kit someone else has put together. Convenient. But what exactly will end up on Ben's machine?
:::

::: step explain
A *plugin* is a bundle of extensions: skills, subagents, hooks, MCP servers. A *marketplace* is a catalogue of plugins, like an app store.

Plugin skills are invoked with the plugin's name: for the `commit-commands` plugin, the command is `/commit-commands:commit`. That way skills from different plugins don't clash.

Claude Code adds the official `claude-plugins-official` catalogue by itself on the first interactive launch.
:::

::: step example
Installing from the official catalogue:

```text
/plugin install commit-commands@claude-plugins-official
```

In a session, this command doesn't install the plugin straight away; it opens its card. The {{data.ui_paths.p2_plugin_will_install}} section shows which commands, agents, skills, hooks and servers it will add. Then you choose a scope.

Plain `/plugin` opens a panel with the {{data.ui_paths.p2_plugin_discover}}, {{data.ui_paths.p2_plugin_installed}}, {{data.ui_paths.p2_plugin_marketplaces}} and {{data.ui_paths.p2_plugin_errors}} tabs.
:::

::: step explain
Now, about trust. The docs say it plainly: an installed plugin can run arbitrary code with your user's privileges.

- Its hooks are shell commands.
- Its MCP servers can run as processes on your machine.
- Its skills and agents enter Claude's context as instructions.

A plugin's hooks and servers run outside the sandbox, and permission rules don't restrain them.
:::

::: step explain
Reading someone else's `hooks.json` and scripts takes a while. You can hand the first pass to Claude: clone the plugin's repository and ask it to examine it without running anything.

But a weak prompt gets a weak review. Improve it so Claude knows what to look at, what not to do and what report to return. Navyk will send your prompt to Claude for feedback.
:::

  task: "A Professional-level learner is improving a prompt for Claude Code: vet a cloned plugin before installation. A plugin can run code with the user's privileges through hooks (hooks/hooks.json), MCP servers (.mcp.json) and executables in bin/, while skills and agents add instructions. R1: it's clear what to check and what decision is being made (install or not). R2: context — where the plugin is, where it came from, why it's being checked. R3: the report format (verdict, list of findings with file and line). R4: what counts as a red flag (network requests to unknown addresses, reading secrets and ~/.ssh, deleting files, downloading and running code, hidden instructions in skills). R8: don't guess; flag what's unclear. R9: an explicit ban on running scripts, installing the plugin or changing anything — read-only. If the prompt asks to run the hooks “to check”, that's an R9 gap."
  criteria: ["R1", "R2", "R3", "R4", "R8", "R9"]
  reference_prompt: |
    The ./turbo-dev folder contains a Claude Code plugin that a colleague sent me from a third-party catalogue. I'm deciding whether to install it. Check it by reading only: don't run, install or change anything.

    Go through these in order:
    1. hooks/hooks.json and every script the hooks call: which events they fire on and which commands they run.
    2. .mcp.json: which servers get started or which addresses they connect to.
    3. Every file in bin/.
    4. Skills and agents: are there any instructions asking Claude to send data elsewhere or get around rules?

    Red flags: network requests to unknown addresses, reading .env, ~/.ssh or other secrets, deleting files, downloading and running code from the internet, obfuscated or encoded code.

    Report: a one-line verdict (“safe to install” / “has risks” / “don't install”), then a list of findings with file, line and a plain-language explanation. If you can't tell what a file does, say so; don't guess.
  show_reference: true
  fallback_feedback:

    - "Are the executed files listed: hooks/hooks.json, scripts, .mcp.json, bin/?"
    - "Did you remember skills and agents, which add instructions?"
    - "Are red flags described: network, secrets, deletion, downloading code?"
    - "Is there an explicit ban on running, installing or changing anything?"
    - "Is the report format set: verdict and findings with files and lines?"

::: step summary
**A plugin is a bundle of skills, subagents, hooks and MCP servers. Install it with `/plugin install <plugin>@<marketplace>`, reading the card and choosing a scope first.**

A plugin runs code with your privileges, so before installing, check the catalogue's source, the {{data.ui_paths.p2_plugin_will_install}} section and the source of its hooks, servers and `bin/`. A catalogue name is no guarantee.

Module complete: you now know every way to extend Claude Code.
:::
