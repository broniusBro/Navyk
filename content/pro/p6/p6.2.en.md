::: step hook
Olivia is building a system for a customer support team: emails come in about payments, delivery and returns. She's wondering whether to build an “agent for everything”.

But most systems on Claude are put together from five simple setups. They're called *patterns*: proven solutions to common problems, like recipes in cooking. Recognising them is quicker than reinventing them.
:::

::: step explain
The first three are the simplest:

- *Prompt chaining*: steps run one after another, and the output of one becomes the input of the next. Write an outline → write the text from the outline → translate it.
- *Routing*: first work out what type of input it is, then send it to the right specialised prompt. An email about a return goes to “returns”.
- *Parallelization*: independent subtasks run at the same time, and the results are combined.
:::

::: step explain
In code, a chain is just a loop. The response from one step becomes the input of the next:

```python
def chain(text: str, prompts: list[str]) -> str:
    result = text
    for prompt in prompts:
        result = llm_call(f"{prompt}\nInput: {result}")
    return result
```

Here `llm_call` is your function that sends a single prompt to Claude and returns the text.
:::

::: step explain
Two more patterns are a bit more involved:

- *Orchestrator-workers*: a lead call breaks down the task itself, decides which subtasks are needed and hands them out to workers. The subtasks aren't known in advance.
- *Evaluator-optimizer*: one call writes (the generator), another checks the result against criteria and gives feedback (the evaluator). The loop repeats until the evaluator accepts the result.
:::

::: exercise match_pairs
id: "p6.2.e1"
type: "match_pairs"
question: "Match each task with the pattern that fits it best."
pairs:
  - left: "Write an article outline, then the text from the outline, then cut it to 300 words"
    right: "Prompt chaining"
    why: "The steps run strictly in order, and each builds on the previous result. Each step is simpler and easier to check."
  - left: "Customer emails: payment questions go to one prompt, returns to another"
    right: "Routing"
    why: "First the input type is identified, then a specialised prompt takes over. Each one can be tuned for its own topic without affecting the others."
  - left: "Evaluate a new pricing plan from the point of view of three customer groups, each separately"
    right: "Parallelization"
    why: "The three evaluations don't depend on each other, so they can run at the same time and the results can be combined. That's faster than one by one."
  - left: "From a product description, decide which copy is needed (website, social media, newsletter) and write each piece"
    right: "Orchestrator-workers"
    why: "The set of subtasks depends on the product, and the lead call chooses it. That's the difference from parallelization, where the subtasks are known in advance."
  - left: "Write code, check it with tests and feedback, fix it until everything passes"
    right: "Evaluator-optimizer"
    why: "There are clear criteria (the tests), and feedback genuinely improves the result. A classic case for a “write → check → fix” loop."
hint: "Look for the key signs: strict order, choice by type, independent parts, subtasks unknown in advance, a loop with checks."
:::

::: exercise single_choice

question: "Olivia needs to answer emails about payments, delivery and returns, and each topic has its own rules. Which pattern suits her?"
options:
  - text: "Routing: first identify the email's topic, then pass it to the prompt for that topic"
    correct: true
    why: "Different topics, different rules. A separate prompt for each can be improved without breaking the others. The first step just picks the path."
  - text: "One huge prompt with all the rules for every topic"
    correct: false
    why: "You could start that way, but the topics' rules get in each other's way: improving answers about returns can easily break answers about payments."
  - text: "Evaluator-optimizer for every email"
    correct: false
    why: "Checking might come in handy later, but Olivia's main problem is different types of email. Routing solves that."
  - text: "An orchestrator that comes up with subtasks from scratch each time"
    correct: false
    why: "The topics are known in advance, and there are three of them. Inventing subtasks anew for every email is unnecessary complexity and extra calls."
hint: "The inputs fall into clear types, and each type needs its own handling. Which pattern picks the path first?"
:::

::: exercise single_choice
id: "p6.2.e3"
type: "single_choice"
question: "How is orchestrator-workers different from parallelization?"
options:
  - text: "The subtasks aren't predefined: the lead call decides them for each specific task"
    correct: true
    why: "Exactly. In parallelization, the set of subtasks is written in code. The orchestrator works it out afresh for every input."
  - text: "The orchestrator's workers always run strictly one after another"
    correct: false
    why: "No, workers can run at the same time too. The difference is who comes up with the subtasks."
  - text: "An orchestrator is always cheaper"
    correct: false
    why: "Quite the opposite: you need at least one extra call for planning. If the subtasks are predictable, parallelization is simpler and cheaper."
  - text: "There's no difference, they're two names for the same pattern"
    correct: false
    why: "They're similar, but the difference is fundamental: who decides the subtasks, the code in advance or the model as it goes."
hint: "Think about where the list of subtasks is written in each pattern."
:::

::: exercise multi_choice
id: "p6.2.e4"
type: "multi_choice"
question: "When is evaluator-optimizer worth using? Select all the right signs."
options:
  - text: "There are clear criteria to evaluate the result against"
    correct: true
    why: "Without criteria, the evaluator will say “looks fine, I guess”, and the loop won't improve anything."
  - text: "The result noticeably improves when it gets feedback"
    correct: true
    why: "If feedback doesn't help, the loop just burns calls. Check on a couple of examples that the revised version is actually better."
  - text: "The model can give meaningful feedback on this task"
    correct: true
    why: "The evaluator is a model too. If it can't clearly say what's wrong, the generator has nothing to work with."
  - text: "You need the fastest possible answer at any cost"
    correct: false
    why: "The loop adds calls and time. When speed matters most, this pattern is a poor choice."
  - text: "The task is one short answer with no quality requirements"
    correct: false
    why: "Then one call is enough. Going round in a checking loop is overkill."
hint: "The loop only works if there's something to compare against and the feedback genuinely helps."
:::

::: exercise find_error
id: "p6.2.e5"
type: "find_error"
question: "Tim has sketched an evaluator-optimizer setup for product descriptions. Tap the weak spots."
prompt: "The generator writes a product description. The evaluator looks at it and says whether it's good or not. If not, the generator writes it again. The loop keeps going until the evaluator says “good”."
segments:
  - text: "The generator writes a product description. "
    weak: false
    why: "It's clear what the first call does. That's how the pattern starts."
  - text: "The evaluator looks at it and says whether it's good or not. "
    weak: true
    why: "There are no criteria. “Good” by what measure? Length, facts from the product page, tone, keywords. Without criteria, the evaluation is random."
  - text: "If not, the generator writes it again. "
    weak: true
    why: "The generator should get the evaluator's feedback and its previous attempt, not start from scratch blind. Otherwise it may repeat the same mistake."
  - text: "The loop keeps going until the evaluator says “good”."
    weak: true
    why: "There's no attempt limit. If the evaluator never says “good”, the loop won't stop and will keep spending money. You need a limit, say 3 rounds, and a plan for what happens after that."
hint: "Check three things: what the evaluation is based on, what the generator gets the second time, and when the loop is guaranteed to end."
:::

::: step summary
**Five patterns: prompt chaining, routing, parallelization, orchestrator-workers, evaluator-optimizer.**

You can combine them. But each one adds calls, so only use a pattern when it noticeably improves the result.
