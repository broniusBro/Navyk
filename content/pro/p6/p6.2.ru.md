::: step hook
Ольга строит систему для службы поддержки: письма приходят про оплату, доставку и возвраты. Она думает, не сделать ли «агента на все случаи».

Но большинство систем на Claude собирают из пяти простых схем. Их называют *паттернами* — проверенными решениями типовых задач, как рецепты в кулинарии. Ты быстрее узнаешь их, чем изобретёшь заново.
:::

::: step explain
Первые три — самые простые:

- *Цепочка* (prompt chaining): шаги по очереди, выход одного — вход следующего. Написать план → по плану текст → перевести.
- *Маршрутизация* (routing): сначала определить тип входа, потом отправить к нужному специализированному промпту. Письмо про возврат — к «возвратам».
- *Параллельные вызовы* (parallelization): независимые подзадачи выполняются одновременно, результаты собираются вместе.
:::

::: step explain
Цепочка в коде — это просто цикл. Ответ одного шага становится входом следующего:

```python
def chain(text: str, prompts: list[str]) -> str:
    result = text
    for prompt in prompts:
        result = llm_call(f"{prompt}\nInput: {result}")
    return result
```

Здесь `llm_call` — твоя функция, которая отправляет один запрос к Claude и возвращает текст.
:::

::: step explain
Ещё два паттерна посложнее:

- *Оркестратор и исполнители* (orchestrator-workers): главный вызов сам разбирает задачу, решает, какие нужны подзадачи, и раздаёт их исполнителям. Подзадачи заранее не известны.
- *Генератор и оценщик* (evaluator-optimizer): один вызов пишет, другой проверяет по критериям и даёт замечания. Цикл повторяется, пока оценщик не примет результат.
:::

::: exercise match_pairs
id: "p6.2.e1"
type: "match_pairs"
question: "Соедини задачу с паттерном, который подходит лучше всего."
pairs:
  - left: "Написать план статьи, по плану — текст, потом сократить до 300 слов"
    right: "Цепочка"
    why: "Шаги идут строго по очереди, и каждый опирается на результат предыдущего. Каждый шаг проще, его легче проверить."
  - left: "Письма клиентов: про оплату — в один промпт, про возврат — в другой"
    right: "Маршрутизация"
    why: "Сначала определяется тип входа, потом работает специализированный промпт. Каждый можно настроить под свою тему, не мешая остальным."
  - left: "Оценить новый тариф глазами трёх групп клиентов, каждую отдельно"
    right: "Параллельные вызовы"
    why: "Три оценки не зависят друг от друга, поэтому их можно сделать одновременно и сложить результаты. Это быстрее, чем по очереди."
  - left: "По описанию товара решить, какие тексты нужны (сайт, соцсети, рассылка), и написать каждый"
    right: "Оркестратор и исполнители"
    why: "Набор подзадач зависит от товара, и его выбирает главный вызов. В этом отличие от параллельных вызовов, где подзадачи известны заранее."
  - left: "Писать код, проверять тестами и замечаниями, исправлять, пока всё не пройдёт"
    right: "Генератор и оценщик"
    why: "Есть ясные критерии (тесты), и обратная связь реально улучшает результат. Классический случай для цикла «написал → проверил → исправил»."
hint: "Ищи ключевые признаки: строгий порядок, выбор по типу, независимые части, подзадачи неизвестны заранее, цикл с проверкой."
:::

options:
  - text: "Маршрутизация: сначала определить тему письма, потом передать его промпту этой темы"
    correct: true
    why: "Темы разные, правила разные. Отдельный промпт для каждой можно улучшать, не ломая остальные. А первый шаг только выбирает путь."
  - text: "Один огромный промпт со всеми правилами для всех тем"
    correct: false
    why: "Так тоже можно начать, но правила тем мешают друг другу: улучшая ответы про возвраты, легко испортить ответы про оплату."
  - text: "Генератор и оценщик для каждого письма"
    correct: false
    why: "Проверка может пригодиться позже, но главная проблема Ольги — разные типы писем. Её решает маршрутизация."
  - text: "Оркестратор, который каждый раз сам придумывает подзадачи"
    correct: false
    why: "Темы известны заранее, их три. Придумывать подзадачи заново для каждого письма — лишняя сложность и лишние вызовы."
hint: "Входы делятся на понятные типы, и каждый тип требует своей обработки. Какой паттерн сначала выбирает путь?"
:::

    correct: false
    why: "Наоборот: нужен как минимум один лишний вызов на планирование. Если подзадачи предсказуемы, параллельные вызовы проще и дешевле."
  - text: "Ничем, это два названия одного паттерна"
    correct: false
    why: "Похожи, но разница принципиальная: кто определяет подзадачи — код заранее или модель по ходу."

    correct: true

  - text: "Модель может дать содержательные замечания по этой задаче"
    correct: true

  - text: "Нужен самый быстрый ответ любой ценой"
    correct: false
    why: "Цикл добавляет вызовы и время. Когда скорость важнее всего, этот паттерн — плохой выбор."
  - text: "Задача — один короткий ответ без требований к качеству"
    correct: false
    why: "Тогда хватит одного вызова. Проверка по кругу тут лишняя."
hint: "Цикл работает, только если есть с чем сравнивать и замечания реально помогают."

::: exercise find_error
id: "p6.2.e5"
type: "find_error"
question: "Тимур описал схему генератора с оценщиком для описаний товаров. Нажми на слабые места."
prompt: "Генератор пишет описание товара. Оценщик смотрит и отвечает, хорошее оно или нет. Если нет — генератор пишет заново. Цикл крутится, пока оценщик не скажет «хорошо»."
segments:
  - text: "Генератор пишет описание товара. "
    weak: false
    why: "Понятно, что делает первый вызов. С этого и начинается паттерн."
  - text: "Оценщик смотрит и отвечает, хорошее оно или нет. "
    weak: true
    why: "Нет критериев. «Хорошее» — по каким признакам? Длина, факты из карточки, тон, ключевые слова. Без критериев оценка случайна."
  - text: "Если нет — генератор пишет заново. "
    weak: true
    why: "Генератор должен получить замечания оценщика и прошлую попытку, а не писать с нуля вслепую. Иначе он может повторить ту же ошибку."
  - text: "Цикл крутится, пока оценщик не скажет «хорошо»."
    weak: true
    why: "Нет предела попыток. Если оценщик ни разу не скажет «хорошо», цикл не остановится и будет тратить деньги. Нужен лимит, например 3 круга, и что делать после него."
hint: "Проверь три вещи: по чему оценивают, что получает генератор во второй раз и когда цикл точно закончится."
:::

::: step summary
**Пять паттернов: цепочка, маршрутизация, параллельные вызовы, оркестратор и исполнители, генератор и оценщик.**

Их можно комбинировать. Но каждый добавляет вызовы, поэтому бери паттерн, только когда он заметно улучшает результат.
